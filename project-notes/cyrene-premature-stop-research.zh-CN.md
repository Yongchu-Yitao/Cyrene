# Cyrene Agent 提前停止：调查与解决方案

日期：2026-09-05。范围：当前源码中的内置 Agent、Goal 控制器及外部 ACP 收尾路径。
本次是研究，未修改运行时代码。以下区分已复现行为、源码证据和待验证建议；没有把某次真实用户会话认定为已定位的事故。

## 结论

普通会话把“模型不再调用工具”当作成功结束的依据，缺少任务完成验收。这能解释模型只说“接下来我会……”却停止的现象。另有确定的协议层缺口：纯文本输出截断也可以进入成功结束路径。

推荐按顺序落实：停止原因分类与截断处理 → 普通任务完成门禁 → 持久化任务义务及有界续跑。提示词调整可以配套，但不能承担唯一保障。长任务继续复用已有 Goal 控制器。

## 已确认的代码路径

| 位置 | 当前行为 | 影响 |
| --- | --- | --- |
| `src/cyrene/core/session.py:4005` `_advance` | 恢复已有 assistant 时，无工具调用就 `_finish_success` | 恢复路径也必须经过未来的完成门禁 |
| `src/cyrene/core/session.py:4196` 附近 | 新模型结果无工具调用就 `_finish_success` | 自然语言承诺、进度汇报和真正交付没有运行时区分 |
| `src/cyrene/core/session.py:4205` `_finish_success` | 只根据 `error` 决定 failed/completed | 不验证文件、计划步骤或其他任务义务 |
| `src/cyrene/core/session.py:4338` 附近 | 收尾后设为 idle，成功显示“已完成”，清空当前请求 | 将回合结束呈现为完成，即使请求尚未执行 |
| `src/cyrene/plugins/model_router.py:239` `_normalized_provider_result` | 截断只在存在原始工具调用时拒绝 | `finish_reason=length` 的纯文本仍可通过 |

`SessionEnd` 也不是现成的停止否决机制：Hook registry 返回各 Hook 的结果，但 `_finish_terminal` 没有把这些结果解释成 allow/continue。应新增明确的结束前决策契约，不能指望在现有 SessionEnd 中返回一个布尔值就生效。

## 最小复现

使用 `uv run python`、临时目录、内存注册的假模型和真实 `AgentSession`：

- 用户请求：“创建 result.txt 并写入 done，然后确认文件存在。”
- 假模型仅返回：“我接下来会创建结果文件。”，`tool_calls=[]`。
- 分别令 `finish_reason` 为 `stop` 和 `length`。
- 两种情况均只调用模型 1 次；Session 变为 `idle`，`session_end_status=completed`；文件不存在。

另对路由归一化做隔离探针，两种响应均放行。该探针用空列表 stub 替换工具解析函数，因为直接调用归一化函数缺少 PluginRuntime 执行上下文；这不是完整供应商链路测试。最初直接调用探针因缺少该上下文失败，修正隔离方式后得到上述结果。

这些结果证明框架会接受未交付的结束响应，不代表所有真实模型每次都会这样输出，也不能证明用户所见的某一轮必然属于这个原因。

## 已有保障与排查边界

- 普通 Session 和 Workbench 配置的 `max_model_calls` 默认是 `None`；因此不能把默认轮数限制当作首要原因。摘要子 agent 有独立的 8 次限制。
- 子 agent manager 的 `has_pending_work` 覆盖未结束子任务、未报告结果及未读 inbox；bridge 在有 pending driver 时抑制完成事件。应扩展既有机制，不重复实现子 agent 等待。
- 流式适配器已有缺失终止事件的检测，会抛出 `ModelStreamError`；网络断流应沿失败诊断路径排查。
- 无效模型响应已有一次重试；耗尽后失败，不是成功。不可将所有失败自动重试成“继续工作”。
- Goal 的 `_drive` 会在回合结束但未提交候选结果时继续；候选结果经 `_review` 验收，不通过会反思再执行。它能解决一部分持续执行问题，但普通聊天不自动享有该控制器。
- 查到本地应用日志中有运行失败记录，但未指定具体提前停止的会话，尚不能关联事故。没有以日志缺少错误作为任务成功的证据。

## 建议实现

### 1. 先修正技术停止原因

归一化供应商结束原因，区分正常文本结束、工具调用、输出截断、拒绝、异常和未知原因；保留原始字段。ACP 也建立明确映射，不把所有非取消原因归为成功。

- 截断纯文本：保留为中间输出，生成可持久化续写触发节点；有界续写后仍截断，显示明确的未完成原因。
- 截断工具调用：继续拒绝执行，要求重新生成完整参数；不能把半截工具调用当作已执行。
- 输出续写必须保留已有有效内容，避免重复拼接；不能只对原触发节点重新调用而丢失部分输出。
- 拒绝、取消、权限不足、等待用户和配额耗尽各走自己的路径，不由完成检查器强制越过。

### 2. 给普通任务加入结束前门禁

在新响应与恢复响应共享的成功收尾入口加入 `BeforeFinish` 或等价的宿主中立契约；Core 负责状态转换，插件负责产品层验收规则。先完成门禁，再执行终结 Hook 和最终投递。

决策至少包含：`allow`、`continue`、`wait`、`blocked`，以及结构化原因、未完成义务、下一步动作和证据引用。

判断顺序：

1. 确定性运行状态：取消、待回答问题、必要后台结果、计划依赖等。
2. 任务相关的客观证据：产物存在、命令退出状态、已要求的验证结果、交付记录。后台服务长期运行不应一概阻止结束；只等待完成任务所必需的结果。
3. 证据不足时对行动型任务调用轻量完成检查器，比较原始请求、已授权范围、实际工具结果和最终回复。明确遗漏时返回具体缺口及可执行下一步，不能只回复“继续”。

纯问答可直接结束；不以“是否调用过工具”作为唯一分类标准，因为“只承诺而零调用”恰恰需要拦截。也不采用“出现接下来三个字就续跑”的关键词规则。

提示词同步明确：进度通过 send_message 发出；工具结果是中间证据；完成所有已授权义务后才发最终回复；需要输入时进入正式提问状态。自检是辅助，完成检查器也可能误判，不能视为证明。

### 3. 有界继续与恢复

- 普通任务门禁先设置可调的有限纠正预算，例如最多 2 次，作为初始实验值而非已验证最佳值。
- 记录可比较的进展证据；重复缺口且没有实质进展时标记未完成/受阻，不静默成功，也不无限发送“继续”。
- 将结束决策、纠正次数、原始请求引用和 continuation 节点持久化；使用 `(run_id, assistant_node_id, policy_version)` 幂等键。
- 验收期间用户新消息、取消或任务版本变化必须使旧决策失效；不得恢复旧授权或重复执行已有副作用。
- 压缩后仍保留任务义务和证据引用，验收依据不能只剩最终总结。
- Goal 自己已拥有续跑和独立验收；普通门禁在 Goal 回合中只处理协议完整性及确定性状态，避免双重语义审查与嵌套循环。
- 检查器不可用时明确保留结果并标记未验证/可恢复，不无限尝试，也不能宣称验收通过。

## 验收与观测

实现完成后用一次相关的 `uv run pytest ...` 运行新增用例及相关现有测试；研究阶段仅做上述最小探针，没有修改或运行全量测试。

必须覆盖：普通问答正常结束；只给计划但未执行被继续；创建产物后缺少用户要求的验证；纯文本截断续写；截断工具不执行；确实缺少用户输入；用户取消；子任务未结束；合法后台服务；连续无进展；纠正预算耗尽；压缩/重启恢复；检查器异常；Goal 不双重循环；ACP 非成功停止原因。

新增诊断事件建议：`finish.proposed`、`finish.checked`、`run.continued`，携带结束原因、决策来源、缺口标识、纠正次数、任务版本及必要证据引用。默认不要复制完整私密上下文。

离线评估使用已标注的真实任务样本，比较提前停止率、已完成任务被误续跑率、额外 token、结束延迟和重复副作用次数。先影子记录门禁结果，再启用明确缺口的拦截；门禁规则不应仅凭少量示例全量上线。
