# 聊天延迟交替对照实验：每版 20 轮

## 判断

本次没有复现此前观测的 **+503 ms**。重构前后完整回复 DOM 中位数为 **927.15 → 925.85 ms**，差 **-1.30 ms**；首段回复 DOM 为 **883.70 → 855.40 ms**，差 **-28.30 ms**。

配对置信区间跨过零，不能据此宣称重构让聊天变快。结果支持撤销将旧三轮观测差作为稳定重构退化证据的做法；不能证明所有模型、负载和平台性能绝对不变。

## 设计与测量边界

- 对照固定提交 `212dcfaa` 与 `ccbdf718`，各使用独立 worktree、数据目录、数据库和插件目录。当前工作区其他任务的业务修改不参与测试。
- 相同已配置的 DeepSeek 模型、参数与对应轮次提示，真实外部调用；不复制用户历史。每版 20 个正式样本，10 个 A/B/B/A 块，一次只执行一个请求。
- 两版各先完成四轮匹配的校准/预热，再开始正式 20 轮。早期探针将旧消息重排误判为首回复，已修正并整体排除该批数据；另外的校准请求不计入正式样本。
- 每次导航后等待上一轮回复确实恢复，再填写输入，避免页面初始化清空刚填入的测试文本。
- 点击时点由真实发送按钮的捕获阶段监听器记录，使用页面 `performance.now()`。Playwright 点击前的稳定性、可用性等待不计入延迟。
- MutationObserver 只识别本轮预期回复的新文本，排除已有助手消息，分别记录首段和完整回复 DOM 时刻。双 rAF 记录后续绘制机会，**不是物理屏幕实际呈现时间**。
- 浏览器原生 Resource Timing 提供请求开始、响应头和响应结束时间；不包装 fetch、不拦截或替换模型流。等待资源计时条目发布后再读取，等待本身不加进延迟。
- 所有样本 `document.visibilityState=visible`；20×2 请求 HTTP 200、预期回复完整、运行状态 done。每轮只有一个模型调用，且时间顺序通过校验。

## 结果

表中均为毫秒，差为当前减基线。中位数之差与配对差的中位数是不同统计量。

| 指标 | 基线中位数 | 当前中位数 | 中位数之差 | 基线 p95 | 当前 p95 |
|---|---:|---:|---:|---:|---:|
| 点击 → 首段回复 DOM | 883.70 | 855.40 | -28.30 | 1168.91 | 1110.12 |
| 点击 → 完整回复 DOM | 927.15 | 925.85 | -1.30 | 1229.76 | 1173.81 |
| 点击 → 完整回复后双 rAF | 959.85 | 950.10 | -9.75 | 1262.15 | 1206.16 |
| 点击 → 请求开始 | 3.15 | 3.30 | +0.15 | 4.11 | 3.93 |
| 点击 → 响应头 | 98.80 | 100.10 | +1.30 | 116.68 | 117.12 |
| 点击 → 响应流结束 | 1022.60 | 989.25 | -33.35 | 1319.53 | 1254.47 |
| 后端 provider_request_sent 阶段 | 241.65 | 250.05 | +8.40 | 284.28 | 290.75 |
| Provider 调用 | 657.66 | 633.65 | -24.01 | 939.58 | 857.15 |
| 请求事件 → 首段回复事件 | 637.27 | 584.59 | -52.68 | 889.28 | 816.20 |
| 首段回复事件 → 回复完成事件 | 66.99 | 64.74 | -2.25 | 71.34 | 78.95 |
| 每轮 bridge_close 减 Provider latency | 316.93 | 321.06 | +4.13 | 364.98 | 375.63 |

后端阶段与页面时钟的起点不同，不能把不同列/指标的中位数直接相加来解释整个请求。Provider 调用包含网络、供应商生成、本地流解析及回调；最后一项也不是纯 CPU 开销。

## 不确定性

按对应轮次配对，以 ABBA 块为单位做 10000 次 bootstrap，每次保留块内两对轮次；随机种子 20260907。以下是配对差中位数及探索性 95% 区间，正数表示当前较慢。

| 指标 | 配对差中位数 ms | 95% 区间 ms |
|---|---:|---:|
| 首段回复 DOM | -39.95 | [-173.35, +48.95] |
| 完整回复 DOM | -19.45 | [-101.80, +50.90] |
| 完整回复后双 rAF | -17.00 | [-117.20, +42.25] |
| 请求开始 | +0.05 | [-0.20, +0.40] |
| 响应头 | +1.35 | [+0.15, +4.10] |
| 后端请求准备阶段 | +2.57 | [-7.86, +10.70] |
| Provider 调用 | -11.34 | [-118.03, +51.13] |
| 其余后端区间近似值 | +3.51 | [-4.82, +8.23] |

响应头有约 1 ms 级的正向差异，不应写成所有指标均无差异；本次没有定位到其确定代码原因，也没有为了消除这种小差异修改业务行为。区间来自仅 10 个块、单机连续会话；未校正多指标比较，不能把其中一项跨零与否当成普遍因果结论。

两版所有正式回复均为 **9 tokens**。每对当前输入比基线少 3 tokens，说明完整模型输入不是逐字节相同；项目路径、运行元数据等仍可能影响请求。19 对缓存命中输入相同，第 12 对当前少 128 cached tokens；主分析保留该样本，没有选择性删除。

## 与旧 +503 ms 读数的关系

旧测法把 Playwright 点击自动等待和约 500 ms 的元素轮询退避计入总时间，又只采了每版三轮。此前已从原数据库确认模型首段等待当时增加约 293 ms，并独立复现轮询放大。

本次扩大样本、交替执行、使用页面内时点后，两版完整回复均约 926 ms，未见稳定的半秒差距。因此应将旧读数保留为一次**受模型波动和测量粒度影响的观测**，不应继续表述为“重构导致聊天慢 503 ms”。也不能把新旧绝对耗时直接相比，宣称应用从 2116 ms 优化到 926 ms：两次计时合同不同。
