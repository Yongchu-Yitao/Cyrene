# Cyrene Agent 性能重构路线图

> 状态：规划中
> 建立日期：2026-08-12
> 范围：Main Agent、模型运行时、工具协议、网络搜索、上下文管理、Workbench 事件与持久化、后台模型任务
> 原则：允许大面积重构内部实现；保持用户数据可迁移、公开行为可解释、权限边界不降低。

## 1. 目标

当前性能问题不是单一慢接口，而是多个放大器串联：工具返回过大，使上下文持续增长；无界 Agent 循环反复发送完整上下文；搜索结果被多次生成和抓取；后台学习、权限审核、事件持久化又与前台运行竞争资源。

本路线图用于逐条消除这些问题。每一项工作都必须形成独立、可验证的变更，完成后在本文更新状态、实测数据和遗留风险。不能以“体感变快”作为完成标准。

本文中的目标架构、模块划分、默认预算和实施顺序都只是候选方案，不代表已经作出技术决策。本轮只登记问题与可选解法，不实施代码修改；每个工作单开始前由项目负责人决定采用、调整、合并或放弃对应方案。

目标架构如下：

```text
User Turn
   │
   ▼
Deterministic Turn Classifier ── pure reply ──► one bounded model call
   │ tool work
   ▼
Agent Run Controller
   ├── Run Budget / Progress Guard
   ├── Context Budget Manager
   ├── Tool Planner + Parallel Scheduler
   └── Search Service
          ├── dedupe/cache
          ├── search results
          └── bounded content extraction
   │
   ▼
Bounded Model Call ──► Final Reply

Background Work Governor
   └── learning / memory / naming / maintenance

Coalesced Event Stream + Incremental Persistence
```

3. 后台模型任务消耗已经超过前台 Main Agent，必须进行统一资源治理。

## 3. 全局验收指标

所有目标都应在固定模型、固定网络环境和固定 fixture 下比较。外部服务时间与 Cyrene 自身开销分开统计。

### 3.1 延迟预算

| 场景 | 目标 |
|---|---:|
| 纯对话 | 单次模型调用；Cyrene 本地额外开销 P95 ≤ 500 ms |
| 单个本地只读工具 | 模型调用不超过 2 次；除工具和模型外开销 P95 ≤ 1 秒 |
| 普通多工具任务 | 默认不超过 8 个模型回合、24 个工具调用 |
| 单次网络搜索 | 默认只发 1 个查询；Cyrene 编排开销 P95 ≤ 1 秒 |
| 搜索任务 | 搜索、抓取、综合各阶段单独计时，不允许隐藏二次模型调用 |
| 首个可见反馈 | P95 ≤ 2 秒；不得依赖先完成长 Phase 1 |

### 3.2 上下文预算

| 项目 | 目标 |
|---|---:|
| 普通 Main Agent 活跃上下文 | 软上限 64K token |
| 普通 Main Agent 活跃上下文 | 硬上限 128K token |
| 单条一般工具结果 | 默认最多 16K 字符 |
| 单条网页正文 | 默认最多 12K 字符 |
| 工具结果在总上下文中的比例 | 通常不超过 50% |
| 同一轮发送给模型的重复内容 | 可检测、可度量，默认不得重复附加完整副本 |

特殊任务可以声明更高预算，但必须显式选择 profile，不能因为模型支持 1M 上下文就自动使用 1M。

### 3.3 稳定性与资源预算

- Main Agent 必须有模型回合数、工具调用数、墙钟时间和无进展熔断器。
- 连续 20 个 benchmark 回合后，进程 RSS 不得随历史长度近似线性增长。
- 高频推理事件写入量相对当前基线下降至少 90%。
- 前台 Agent 活跃时，后台模型任务不得占用同一模型候选的前台并发配额。
- 所有自动降级、重试、搜索 fallback 和额外修复调用都必须在 telemetry 中可见。

## 4. 重构边界与设计原则

1. **预算优先**：任何模型调用、工具调用、搜索、上下文或后台任务都必须归属一个显式预算。
2. **结构化结果优先**：工具返回 `ToolResultEnvelope`，大内容写入 Artifact/Blob Store，模型只接收摘要、引用和按需读取句柄。
3. **调用前治理**：上下文裁剪必须发生在每次模型调用前，不能只在持久化时补救。
4. **一次生成**：搜索层返回证据，回答层负责综合；避免搜索模型和 Main Agent 重复写答案。
5. **前台优先**：后台学习、记忆和命名统一进入低优先级调度器。
6. **可观察**：端到端时间必须分解为本地准备、模型排队、TTFT、生成、工具排队、工具执行、结果等待和持久化。
7. **安全不退化**：性能重构不得通过取消权限校验、减少来源验证或静默吞掉失败来提速。
8. **内部 API 可重写**：不为保留低效的内部函数形状而牺牲目标架构；必要时提供短期适配层并明确删除日期。

## 5. 目标模块

建议先建立以下边界，再迁移旧逻辑：

| 新模块 | 责任 |
|---|---|
| `agent/run_controller.py` | 生命周期、预算、回合状态、终止原因、无进展检测 |
| `agent/turn_router.py` | 确定性路由；决定纯对话、工具任务、研究任务和需澄清任务 |
| `model_runtime/context_budget.py` | 每次调用前的 token 预算、摘要、去重和工具结果投影 |
| `tooling/result_envelope.py` | 统一工具结果、预览、Artifact 引用、错误和截断元数据 |
| `tooling/batch_scheduler.py` | 依赖图、资源冲突、并发执行、完成顺序消费 |
| `search/service.py` | 查询预算、去重、缓存、Provider、证据标准化、抓取策略 |
| `runtime/background_governor.py` | 前后台优先级、并发额度、空闲检测、取消与恢复 |
| `observability/event_coalescer.py` | 高频 Delta 合并、采样、持久化和重放 |
| `workbench/incremental_store.py` | 增量消息、事件和状态持久化，替代热路径整文件重写 |

文件名可以调整，但责任边界不应重新混入单个超大 Agent 函数。

## 7. 逐项问题与工作单

状态值：`待办`、`进行中`、`已完成`、`阻塞`、`不做`。

### P-001 建立可重复的性能基准

- 状态：已完成（2026-08-12）
- 问题：当前数据来自真实会话，无法稳定比较提交前后变化。
- 改造：增加纯对话、单工具、多工具、单搜索、搜索加抓取、长历史、超大工具结果、后台竞争八类 fixture；允许使用确定性假模型和可控延迟 HTTP Server。
- 验收：一次命令输出 JSON 和 Markdown 报告，包含端到端时间、模型回合、工具数、Prompt Token、事件数、RSS 增量。
- 建议测试：新增 `tests/performance/`，避免把真实凭据测试放入默认 pytest。
- 依赖：无。

完成记录：

- 命令：`uv run python -m cyrene.observability.performance_benchmark --output-dir output/performance --repeats 3`
- 输出：同名 JSON 与 Markdown 报告。
- 场景：纯对话、单工具、多工具、WebSearch、搜索加抓取、长历史、超大工具结果、后台竞争。
- 指标：端到端墙钟、模型回合、工具调用数、Prompt Token 总量/峰值、事件数、RSS 增量、Trace Span 数。
- 隔离：使用确定性假模型和假工具，不读取真实凭据、不访问网络、不写生产会话。
- 说明：本项只建立基线，不引入性能回归阈值；阈值仍属于 P-006。

### P-002 统一端到端 Trace ID 与阶段计时

- 状态：已完成（2026-08-12）
- 问题：模型、搜索、工具、事件和 Workbench Run 使用不同 ID，人工关联成本高。
- 改造：定义 `run_id → round_id → model_call_id/tool_call_id/search_id`；统一记录本地准备、排队、TTFT、生成、执行、消费、持久化。
- 验收：任意慢 Run 可用一条查询生成完整瀑布图，所有额外模型调用可追踪到原因。
- 依赖：P-001。

完成记录：

- 新增 `runtime_trace_spans` 追加式遥测表，以 `trace_id` 查询整条瀑布。
- 同一 Run 的非模型 Span 先在 Run 上下文内缓冲，根 Span 结束时单事务写入，避免为每个阶段新开 SQLite 连接；模型 Span 复用已有 LLM 遥测批次。
- 层级：Workbench `run_id` 作为根 Trace，向下关联 Agent Round、工具执行/消费、搜索 `search_id`、搜索 Provider/检索/抓取/过滤/综合和模型尝试。
- 模型阶段保留排队、请求、响应头、TTFT、首 Token、生成、重试退避及 Token 计数。
- 工具阶段记录排队、执行、结果大小和消费等待；Run 单独记录最终持久化阶段。
- Trace 属性禁止写入提示词、搜索正文、URL、工具正文和密钥，仅保留诊断元数据。
- 查询入口：`await cyrene.runtime.database.get_runtime_trace(db_path, trace_id)`。
- 说明：本项不增加循环预算、无进展检测、输出上限或回归门槛；P-003 至 P-006 均未在本批实现。

### P-003 给 Main Agent 增加硬预算

- 状态：待办
- 问题：主循环是无界 `while True`，没有回合、工具、时间或无进展上限。
- 改造：引入 `RunBudget`；默认最大 8 个模型回合、24 个工具调用、180 秒、连续 3 个无进展回合。研究和显式长任务使用独立 profile。
- 验收：构造永远继续调用工具的假模型，Agent 必须以结构化 `budget_exhausted` 结束并保留可用结果。
- 依赖：P-002。

### P-004 建立无进展检测器

- 状态：待办
- 问题：重复搜索、重复读取、相同失败和无状态变化不会触发停止。
- 改造：对工具名、规范化参数、结果摘要和可见状态变化计算指纹；识别重复调用和失败振荡。
- 验收：连续相同搜索、相同 Bash 失败或相同页面抓取最多允许重试一次，随后改变策略或结束。
- 依赖：P-003。

### P-005 所有模型输出设置用途级上限

- 状态：待办
- 问题：Phase 1、Phase 2、搜索、命名、修复、研究等大量调用使用 `max_tokens=None`。
- 改造：定义 `ModelCallProfile`，例如 router、tool_step、final_reply、search_filter、research_section；每类设置输出上限和 thinking 策略。
- 验收：代码扫描不再允许业务调用裸传 `max_tokens=None`，除非附带显式豁免和测试。
- 依赖：P-001。

### P-006 增加性能回归门槛

- 状态：待办
- 问题：当前测试主要验证正确性，缺少回合数、上下文大小和事件量回归断言。
- 改造：在确定性 fixture 上断言预算，不使用易抖动的严格墙钟值；CI 保存趋势 Artifact。
- 验收：引入额外模型回合、无限工具结果或事件爆炸的提交会稳定失败。
- 依赖：P-001、P-002、P-003、P-005。

### P-007 工具结果默认硬上限

- 状态：待办
- 问题：`MAX_TOOL_OUTPUT_CHARS=0` 表示无限，单条结果可达到数十万字符。
- 改造：删除“0 等于无限”的默认行为；一般工具默认 16K 字符，按工具 profile 设置更小限制。截断必须保留总长度、摘要和 Artifact 引用。
- 验收：任何未经显式豁免的工具结果都不能把超过预算的正文放入模型消息。
- 依赖：P-001。

### P-008 引入 `ToolResultEnvelope`

- 状态：待办
- 问题：工具只返回字符串，运行时无法区分摘要、正文、二进制、错误和可延迟读取内容。
- 改造：统一结构包含 `status`、`summary`、`preview`、`content_ref`、`content_type`、`size`、`truncated`、`citations`、`diagnostics`；保留旧字符串适配器用于迁移。
- 验收：Main Agent 上下文只接收 envelope 的模型投影；完整内容存入 Artifact/Blob Store。
- 依赖：P-007。

### P-009 大结果改为按需分页读取

- 状态：待办
- 问题：Read、Bash、WebFetch、MCP 结果可能一次塞入完整正文。
- 改造：提供稳定 `content_ref` 和范围读取；Agent 可按行、字符、章节或 JSON Pointer 继续读取。
- 验收：读取 1 MB 文件时，单次模型上下文增长不超过配置预算；后续页不会重复发送前页。
- 依赖：P-008。

### P-010 每次模型调用前执行上下文预算

- 状态：待办
- 问题：机械压缩主要发生在会话保存阶段，当前执行轮仍会无限增长。
- 改造：`ContextBudgetManager.prepare()` 成为模型运行时强制入口；任何 caller 都不能绕过。
- 验收：在同一轮连续产生大型结果时，每次实际发送 Prompt 都保持在 profile 硬上限内。
- 依赖：P-008、P-009。

### P-011 将压缩阈值与模型最大窗口解耦

- 状态：待办
- 问题：DeepSeek V4 的 1M 窗口使自动压缩到约 600K 才触发。
- 改造：同时维护模型物理窗口和产品工作预算；普通 Agent 默认 64K/128K，不随物理窗口扩大。
- 验收：1M 模型上的普通会话仍在 64K 软预算附近运行。
- 依赖：P-010。

### P-012 真正执行历史消息预算

- 状态：待办
- 问题：`MAX_HISTORY_MESSAGES` 配置存在，但模型投影没有按消息数或 token 有效裁剪。
- 改造：移除容易误导的单一消息数配置，改为最近回合、固定事实、任务状态和 token 预算的组合策略。
- 验收：长会话中旧工具 episode 被摘要或引用替代；最近用户约束和未完成任务状态完整保留。
- 依赖：P-010、P-011。

### P-013 上下文去重

- 状态：待办
- 问题：系统块、执行 brief、搜索答案、工具输出和最终摘要可能重复表达相同内容。
- 改造：对稳定上下文块和工具结果计算内容指纹；模型请求构建时去重，保留 provenance。
- 验收：Trace 报告 `deduplicated_tokens`，相同正文不会在同一请求中出现两份。
- 依赖：P-010。

### P-014 将上下文持久化与模型投影分离

- 状态：待办
- 问题：UI 历史、审计历史和模型上下文共享近似消息结构，导致为了重放而保存的内容进入模型。
- 改造：定义 `ConversationRecord`、`AuditRecord`、`ModelContextItem` 三种投影；持久化完整事实，模型只接收预算后的语义视图。
- 验收：UI 能看到历史工具活动，但旧工具原文不再自动进入模型请求。
- 依赖：P-008、P-010。

### P-015 删除普通请求的模型化 Phase 1

- 状态：待办
- 问题：每个普通任务先支付一次平均约 23.2 秒的规划调用。
- 改造：用确定性 Turn Classifier 处理纯对话、显式工具请求、显式研究、显式问用户；模糊任务直接进入一个具备工具的模型回合，不再先调用规划模型。
- 验收：纯对话只有一次模型调用；显式工具任务第一轮模型可直接调用实质工具。
- 依赖：P-003、P-005、P-010。

### P-016 缩小首轮工具 Schema

- 状态：待办
- 问题：Phase 1 和 Phase 2 都携带 30 个工具、约 21.7K 字符 Schema。
- 改造：Turn Classifier 选择最小稳定工具包；Direct Tool 也按领域包投影。评估 Provider prefix cache 后，用实测决定稳定前缀粒度。
- 验收：常见文件任务首轮 Schema 显著小于全量 bundle，且工具选择正确率不下降。
- 依赖：P-015。

### P-017 将规划状态结构化

- 状态：待办
- 问题：Phase 1 execution brief 作为长文本再次注入 Phase 2，容易重复和漂移。
- 改造：使用紧凑 `RunPlan`：目标、验收、已知事实、下一步、风险、状态版本；仅在计划变化时更新。
- 验收：计划内容不会在每轮重复增长，Trace 可显示计划版本差异。
- 依赖：P-015。

### P-018 合并细碎工具步骤

- 状态：待办
- 问题：近期单轮出现 39 次 Bash，大量步骤各自触发一次模型往返。
- 改造：为常见只读检查提供批量调用；Prompt 和 scheduler 鼓励同批独立调用；Shell 支持结构化多命令但保持权限逐项校验。
- 验收：代表性代码审计 fixture 的模型回合和 Bash 次数至少下降 50%。
- 依赖：P-003、P-008。

### P-019 重构渐进工具发现协议

- 状态：待办
- 问题：简单能力也强制 `discover → describe → invoke`，产生 2–3 个额外模型回合。
- 改造：Run 内维护已披露能力缓存；高频、低风险能力可由 router 预披露；允许 `discover` 返回选中能力的最小调用 schema。
- 验收：发送文件等已知简单任务不超过一次发现往返；能力权限仍在执行层校验。
- 依赖：P-016、P-017。

### P-020 用依赖图替代默认顺序屏障

- 状态：待办
- 问题：许多工具默认 `requires_order=True`，可并行操作被保守串行化。
- 改造：工具声明读写资源、前置依赖和副作用；scheduler 根据 DAG 执行，不再把未知顺序作为全局屏障。
- 验收：独立只读和独立文件写入可以并行；冲突写入仍稳定串行。
- 依赖：P-008。

### P-021 按完成顺序消费并行结果

- 状态：待办
- 问题：快速结果会等待原始列表中更慢的前置工具，已观测最长排队约 70.5 秒。
- 改造：scheduler 发布完成流；Agent 可先处理可用结果，同时保持最终工具协议顺序的合法投影。
- 验收：后完成的慢搜索不阻止先完成结果进入 UI；结果队列延迟 P95 接近零。
- 依赖：P-020。

### P-022 简化最终回复协议

- 状态：待办
- 问题：`quit`、正文和工具协议不匹配时会追加一到两次完整历史修复调用。
- 改造：把终止状态从模型工具调用移到 Run Controller；模型无工具时自然结束，最终正文采用一次受限修复或确定性 fallback。
- 验收：正常任务不产生 final-repair 模型调用；异常路径最多一次，并使用压缩后的结果摘要。
- 依赖：P-003、P-015。

### P-023 优化运行中用户指导

- 状态：待办
- 问题：新指导可能取消并重启整次模型调用，丢弃已生成工作。
- 改造：区分“追加约束”“替换目标”“立即停止”；追加约束优先在安全边界合并，只有替换目标才取消当前调用。
- 验收：连续追加非冲突约束不会重复支付完整模型调用；取消原因在 Trace 中明确。
- 依赖：P-003、P-017。

### P-024 建立统一 Search Service

- 状态：待办
- 问题：搜索 Provider、网页抓取、LLM 过滤和综合混在 `WebSearch` 后端中，成本不可见。
- 改造：定义 `SearchRequest`、`SearchEvidence`、`FetchRequest`、`SearchBudget`；Provider 只负责检索或返回可标注的原生答案。
- 验收：每个阶段单独计时、计费和记录来源；Main Agent 能选择只要链接、摘要或正文证据。
- 依赖：P-002、P-008。

### P-025 默认单查询并限制搜索扇出

- 状态：待办
- 问题：Agent 对同一主题发起 2–7 个高度重叠查询。
- 改造：普通搜索预算为 1 个查询；研究 profile 才允许扩展，并设总查询数与并发数。
- 验收：普通事实查询只调用一次 Provider；扩展搜索必须在 Trace 中说明新增查询覆盖的未知项。
- 依赖：P-024。

### P-026 查询规范化、去重和短期缓存

- 状态：待办
- 问题：同一会话和相邻任务不会复用相同或近似搜索。
- 改造：规范化语言、空白、时间范围和域名过滤；建立按 Provider、查询、时效策略区分的 TTL Cache。
- 验收：相同查询在 TTL 内命中缓存；时效敏感请求可显式绕过；引用仍保留检索时间。
- 依赖：P-024。

### P-027 原生搜索设置输出与时间预算

- 状态：待办
- 问题：DeepSeek 原生搜索无输出上限，整体超时 120 秒。
- 改造：设置短答案输出上限、连接/首字节/总时间分段超时；超时返回已有证据，而不是等待完整长文。
- 验收：默认搜索不会生成数千 token 长答案；达到预算时返回结构化 timeout/partial 状态。
- 依赖：P-005、P-024。

### P-028 复用搜索 HTTP 客户端

- 状态：待办
- 问题：原生搜索和 WebFetch 每次新建 Client，重复连接和 TLS 握手。
- 改造：按事件循环和网络策略复用连接池，限制每 Host 并发和 Keepalive。
- 验收：连续搜索的连接复用率可观测；关闭应用时客户端被正确清理。
- 依赖：P-024。

### P-029 重写 WebFetch 为正文提取器

- 状态：待办
- 问题：当前返回完整 HTML/JSON，没有正文提取或响应体上限。
- 改造：先检查 Content-Type 和 Content-Length；流式读取到硬上限；HTML 提取正文、标题、发布日期和 canonical URL；JSON 提供路径摘要；二进制拒绝或转 Artifact。
- 验收：典型新闻、文档、GitHub、PyPI 页面不会把导航和脚本塞入模型；模型投影 ≤ 12K 字符。
- 依赖：P-008、P-024。

### P-030 消除搜索的重复综合

- 状态：待办
- 问题：Provider 已写完整答案，Main Agent 又抓取并再次综合。
- 改造：优先让搜索层返回结构化证据和短摘要；若 Provider 只能返回答案，标记其生成性质，Main Agent不得默认再次抓取所有链接。
- 验收：普通搜索最多发生一次回答生成；需要核验时只抓取关键来源。
- 依赖：P-024、P-029。

### P-031 简化 SimpleXNG fallback

- 状态：待办
- 问题：一次 fallback 隐含搜索、最多 8 次抓取、一次 LLM 过滤和一次 LLM 综合。
- 改造：默认直接返回前 5 个标准化结果；规则过滤优先；只有调用方请求答案综合时才进行一次模型调用。
- 验收：fallback 的隐藏模型调用数默认为零；所有额外阶段由 `SearchBudget` 授权。
- 依赖：P-024、P-029、P-030。

### P-032 建立前后台资源治理器

- 状态：待办
- 问题：技能学习当日模型服务时间约为 Main Agent 的两倍，与前台共享资源。
- 改造：统一管理 main、permission、search、learning、memory、naming、steward；设置优先级、并发额度和抢占规则。
- 验收：前台 Run 活跃时低优先级模型任务不启动新调用；已有低优先级任务可安全暂停或取消。
- 依赖：P-002、P-005。

### P-033 重构行为学习调度

- 状态：待办
- 问题：每 10 分钟扫描，清会话时再次触发；积压可产生大量连续模型调用。
- 改造：事件驱动记录候选，空闲窗口批处理；设置每日 token、调用数和墙钟预算；失败使用持久退避。
- 验收：无新可学习证据时零模型调用；前台压力下自动延后；积压不会一次耗尽模型额度。
- 依赖：P-032。

### P-034 合并权限审核调用

- 状态：待办
- 问题：自动权限模式可能对同一任务的多个相似边界逐次调用审核模型，今天出现 95 次。
- 改造：优先使用确定性规则；对同一 Run、相同风险级别和资源范围签发短期、参数绑定的批量审核票据；高风险仍由人确认。
- 验收：代表性多文件任务审核调用下降至少 70%，且没有扩大授权范围。
- 依赖：P-017、P-032。

### P-035 降低命名、记忆和研究后台竞争

- 状态：待办
- 问题：会话命名、项目记忆、旧式记忆压缩和 Research 扩写都有额外无界模型调用。
- 改造：命名优先本地规则并异步优化；记忆学习只在空闲时运行；Research 使用独立预算和最大章节并发。
- 验收：首轮回复不等待会话命名；记忆任务不占前台并发；Research 总调用数可在开始前估算。
- 依赖：P-005、P-032。

### P-036 合并推理流事件

- 状态：待办
- 问题：一天产生 71,347 条 reasoning delta，每条都进入内存、前端和数据库路径。
- 改造：按 50–100 ms 或字符阈值合并；UI 实时流与持久审计采用不同粒度；默认只持久化合并块或最终 reasoning 摘要。
- 验收：同一 benchmark 的持久事件数下降至少 90%，视觉流畅度不下降，断线重连仍能收敛。
- 依赖：P-002。

### P-037 将热路径持久化改为增量存储

- 状态：待办
- 问题：会话状态和聊天文档经常整份 JSON 序列化、读取和替换。
- 改造：消息、运行、事件和 Materialized View 分表或追加日志；JSON 仅作为导出/兼容镜像，异步低频生成。
- 验收：写入一条中间消息的 I/O 与总历史大小无关；崩溃恢复不依赖完整重写成功。
- 依赖：P-014、P-036。

### P-038 增量化工作区变更检测

- 状态：待办
- 问题：每个 Run 开始和结束都遍历工作区并读取/哈希大量文件。
- 改造：优先使用工具执行时记录的 touched paths；补充文件系统事件或 Git 状态；只有无法归因时进行有界扫描。
- 验收：无文件改动的聊天不扫描整个工作区；大型仓库的首尾本地开销不随文件总数线性增长。
- 依赖：P-002、P-014。

### P-039 内存、数据库与保留策略收口

- 状态：待办
- 问题：大型上下文、事件副本、会话 JSON 和后台数据库使 RSS 与存储持续增长。
- 改造：明确 Run 结束后的对象释放；大型正文只保留一个 Blob 副本；对事件和学习数据库设置保留、归档、VACUUM/Checkpoint 策略；增加泄漏 benchmark。
- 验收：连续 20 个固定回合后的 RSS 进入稳定平台；删除/过期数据后空间可回收；恢复功能不受影响。
- 依赖：P-008、P-036、P-037。

## 8. 每一项的执行模板

后续逐条解决时，统一按以下流程，避免同时改动过多而无法归因：

1. 将一个工作单状态改为 `进行中`，记录负责人和开始日期。
2. 用 P-001 fixture 记录该项改造前的数据。
3. 写一页以内的具体设计决策；若改变协议或存储格式，补 ADR/迁移方案。
4. 完成全部代码修改和自审后，只运行一次与改动范围相称的聚焦测试。
5. 运行同一 fixture，比较模型回合、Prompt Token、工具结果体量、事件数、墙钟时间和 RSS。
6. 满足验收标准后改为 `已完成`，记录提交、数据和遗留风险。
7. 如果指标没有改善，不以“代码更整洁”为由关闭性能工作单。

完成记录模板：

```markdown
#### P-XXX 完成记录

- 状态：已完成
- 完成日期：YYYY-MM-DD
- 相关提交/PR：
- 改造前：
- 改造后：
- 测试命令：
- 遗留风险：
```

## 9. 建议的首批实施顺序

第一批建议严格按以下顺序推进：

1. P-001：建立 benchmark。
2. P-002：统一 Trace。
3. P-003、P-004：先阻止失控循环。
4. P-007、P-008：封住无限工具结果。
5. P-010、P-011、P-012：把上下文预算移到每次模型调用前。
6. P-015、P-022：移除普通 Phase 1 和脆弱的最终回复协议。
7. P-024、P-029、P-030、P-031：重写搜索链路。
8. P-032、P-033、P-034：治理后台和权限模型调用。
9. P-036、P-037、P-039：处理事件、持久化和内存。

这条顺序优先切断乘法效应：先限制单条数据，再限制上下文，再限制循环次数，最后优化单个 Provider 和本地 I/O。仅先把 WebSearch 超时从 120 秒改小，会更快失败，但不会解决 Agent 整体变慢。

## 10. 迁移与兼容策略

- `ToolResultEnvelope` 上线期间允许旧字符串 handler，通过适配器转换；新工具不得再使用裸字符串协议。
- 会话存储迁移必须可从旧 `state.json` 和 Workbench Document 恢复；首次读取可惰性迁移，不覆盖原备份。
- 新 Run Controller 上线时保留 Feature Flag，先在 Workbench Chat 灰度，再覆盖 Scheduler、Quick Chat 和远程渠道。
- Search Service 应先兼容现有 DeepSeek 与 SimpleXNG Provider，再删除旧 `deep_search()` 多阶段实现。
- Telemetry Schema 采用可追加迁移；迁移失败不得阻止用户读取已有对话。
- 正式切换后删除旧 Phase 1、旧字符串工具结果热路径和旧整文件热写路径，避免双实现永久共存。

## 11. 不作为主要优化方向的事项

以下事项可以优化，但当前证据表明不是第一优先级：

- SQLite WAL 配置；当前没有显示它是主要端到端瓶颈。
- SimpleXNG 子进程自身资源占用；当前进程占用较低。
- 单纯增加模型并发；在上下文和后台任务未治理前，只会加剧上游竞争。
- 单纯依赖 Prompt Cache；它不能消除请求序列化、传输、上下文管理和长输出。
- 单纯换更快模型；无界回合、重复搜索和超大工具结果仍会保留。

## 12. 完成定义

本路线图只有在以下条件全部满足时才算完成：

- P-001 至 P-039 均有明确终态和完成记录。
- 普通 Agent 不再拥有无界模型/工具循环。
- 工具和网页原文不会无界进入模型上下文。
- 普通请求不再强制支付模型化 Phase 1。
- 搜索不存在默认的隐藏二次综合和无预算扇出。
- 后台模型任务由统一治理器调度，不与前台争抢并发。
- 高频事件和消息持久化成本不再随 token/历史条数一比一增长。
- 正式架构文档、配置文档和性能测试与新实现一致。
