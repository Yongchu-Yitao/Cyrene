# 聊天观测增加 503 ms 的调查

后续已完成每版 20 轮页面内计时的交替实验，见 [ABBA 对照结果](chat-latency-ab-2026-09-07.zh-CN.md)：完整回复 DOM 中位数 927.15 → 925.85 ms，未复现 +503 ms；原调查数据保留如下。

## 结论

503 ms 是原 Playwright 脚本的观测中位数差，不能直接作为应用绘制或重构性能回归值。复查原六次运行的持久化事件，并做无模型浏览器实验后，证据支持两个同时存在的因素：

1. 当前版所处时间窗口的模型调用确实更慢，差异集中在首段回复之前。
2. Playwright 元素等待带有约 500 ms 的后期轮询间隔，会使观测呈阶梯变化。

这批记录没有显示发送准备、首段之后的输出或其余后端区间增加半秒。仍不能用每版三轮、非交替执行的样本证明重构绝对没有性能影响，也不能将模型区间的差异完全归因于供应商服务器。

## 原始观测与测量缺陷

原脚本从调用 `button.click()` 前开始用 Node 的 `Date.now()` 计时，随后通过 `getByText(token).last().waitFor({state:"visible"})` 等待完整短回复。因此读数包含点击自动等待、模型调用、DOM 更新、元素轮询和跨进程通信；并非浏览器实际绘制时间戳，也不是首 token 指标。

| 版本/轮次 | click 返回 ms | 观测到回复 ms | click 返回后的等待 ms |
|---|---:|---:|---:|
| 基线 1 | 230 | 1019 | 789 |
| 基线 2 | 825 | 2115 | 1290 |
| 基线 3 | 827 | 1613 | 786 |
| 当前 1 | 24 | 1313 | 1289 |
| 当前 2 | 831 | 2119 | 1288 |
| 当前 3 | 827 | 2116 | 1289 |

回复观测中位数为 1613 → 2116 ms，差 503 ms；等待时间集中在约 790/1290 ms 两档。约 825 ms 的 click 返回等待也不能解释成应用处理点击用了 825 ms。

## 从当时实际运行记录拆解

只读原隔离数据库 `browser-before/store/cyrene.runtime.database` 和 `browser-after/store/cyrene.runtime.database`。按照运行顺序排除预热，取三轮 `CYRENE_ROUND_1/2/3`。解码 `workbench_chat_run_events`，读取 `chat_timing`、`reply_delta`、`reply_done` 与 `llm_call.response`，没有重新调用外部模型，也没有用另一次测试替换原数据。

| 指标，中位数 | 基线 ms | 当前 ms | 差 ms |
|---|---:|---:|---:|
| snapshot_complete 阶段 | 89.232 | 84.122 | -5.110 |
| provider_request_sent 阶段 | 170.209 | 163.945 | -6.264 |
| 请求事件至首个 reply_delta 事件 | 541.537 | 834.207 | +292.670 |
| 首个 reply_delta 至首个 reply_done 事件 | 69.279 | 64.697 | -4.582 |
| Provider 调用 latency_ms | 590.479 | 874.173 | +283.694 |
| agent_bridge_close 阶段 | 818.976 | 1110.120 | +291.144 |
| 每轮 bridge_close 减 Provider latency 后再取中位数 | 238.522 | 235.161 | -3.361 |

最后一行是近似的其余后端区间，包含准备及桥接收尾，不是独立 CPU profiler 结果。不同指标的时钟起点与区间不同，独立中位数不可相减后拼成“503 = 模型 X + 浏览器 Y”的精确分解。

Provider latency 在 `_shared.py` 中从调用开始计到流完成后的规范化结果，包含网络、供应商生成、本地解析和回调，不能称为纯网络延迟。`provider_request_sent` 也是应用事件边界，不是抓包测得的请求最后一字节发送时间。

两版三轮输出均为 8 tokens，缓存命中输入分别同为 4864/4992/5248 tokens；输入总 tokens 仅后两轮相差 1–2，未出现输出明显变长或缓存失效。此次 DeepSeek 走的共享 Provider 实现 `_shared.py` 在基线与重构提交之间没有变更。两组调用发生在不同时间窗口，未采用交替或随机顺序，因此现有证据更支持模型调用首段等待波动，仍不能单凭这点证明完整调用上下文等价。

## 独立复现 Playwright 观测阶梯

检查实际安装的 `@playwright/cli 0.1.19` 对应 playwright-core：`waitForSelector` 使用 `retryWithProgressAndBackoff`，退避序列为 `[20,50,100,100,500]`，随后重复最后的 500 ms 间隔。

在空白 Chromium 页面里用定时器更新一个可见段落；页面内 `performance.now()` 记录真实 DOM 更新时刻，使用与原脚本相同的 `getByText(...).waitFor({state:"visible"})` 观测。实验不加载 Cyrene、不连接模型：

| 计划更新 ms | 实际 DOM 更新 ms | Playwright 返回观测 ms | 检测滞后 ms |
|---|---:|---:|---:|
| 600 | 602.1 | 790.3 | 188.2 |
| 800 | 801.5 | 817.7 | 16.2 |
| 900 | 901.7 | 1295.7 | 394.0 |
| 1100 | 1101.7 | 1293.4 | 191.7 |
| 1300 | 1301.4 | 1792.7 | 491.3 |

其中实际 DOM 更新从 1101.7 增到 1301.4 ms，约增加 200 ms，观测却约增加 499 ms。确证这种测法可以放大跨越轮询边界的差异；不意味着原 503 ms 全都是自动化误差。

## 下一次性能验收应采用的测量合同

- 将 click、请求发送、首段到达、DOM 更新、首帧机会、完整回复分别计时。开始时间放在真实点击事件处理器中，使用页面 `performance.now()`，排除 Playwright 点击前的自动等待。
- 用页面内 MutationObserver 记录 DOM 更新，必要时结合 rAF/PerformanceObserver；这些也不等于物理屏幕已呈现，需明确指标定义。Playwright 仅负责等待完成与读取已记录时间，不负责产生延迟读数。
- 补齐每个 run 的客户端时间戳；已有 first_dom_paint 上报并非每轮都有，本次六轮不能恢复精确浏览器绘制耗时。
- 两版交替 A/B/B/A，匹配项目、模型参数、消息历史和预热条件，至少各 20–30 次，报告分布和置信区间，避免以三轮中位数作回归判定。
- 同时保留固定模型流的端到端测试以隔离本地开销，及真实模型测试以评估用户体验；固定流不能替代真实供应商验收。
