# Cyrene 全面性能复查与剩余优化清单

2026-09-20。本轮是研究，不是又一次产品修改。保留“不减少任何功能、不改变界面和动画”的约束；所有新原型只在临时数据或实验进程中运行。

## 结论

之前完成的是 **现代实时消息投影末尾的有序合并**，不是整个聊天链路的优化。此次核对历史材料、检查当前源码并补做实验后，列出 **10 类尚未完成的候选**：9 类有局部测量证据，另 1 类只有剖析线索，不能直接承诺收益。它们不是 10 个影响所有用户的已确认故障，触发负载和优先级不同。

尤其需要补充两点：

1. **同一种平方增长合并仍存在于“完成保存”和旧协议投影路径。** 之前为控制影响范围只改了一个调用点；该决策保留了兼容性，但留下了明确的性能覆盖缺口。
2. **长列表渲染仍然昂贵。** 消息合并变快后，全部消息组件的重新执行和初次布局成为更明显的剩余成本。不能把一次投影的百倍提升解释成整个 agent 同比加速。

下一批最值得实施的是：保存/旧协议的受保护合并、关闭日志级别的提前判断、后端结构事件的局部变更检测。渲染与终端解析的潜在收益更大，但涉及更多行为边界，需要分开验证。

## 1. 同一个合并问题还有两个未覆盖调用点

当前源码：`frontend/features/chat/runtime-timeline.jsx`。

- `wbcProjectTranscript` 已调用 `wbcMergeProjectedMessages`。
- `wbcMergeSavedAssistantMessages` 仍调用 `wbcMergeChronologicalMessages`。
- `wbcProjectRuntimeTranscript` 仍调用 `wbcMergeChronologicalMessages`。
- `runtime-page-hooks.jsx` 的 `wbcRuntimeAssistantSaved` 会为详情缓存、活动会话分别执行保存合并。两个对象均存在时可能重复付出成本；本轮没有测整段终态交接，不能直接把微基准乘二当作实际 UI 延迟。

同一 JS realm、普通有序记录，每组预热 2 次并保留 7 次；逐次核对输出完全等于全部输入消息：

| 历史＋新增 | 现代实时投影 | 保存合并 | 旧协议投影 |
|---|---:|---:|---:|
| 1000＋40 | 0.388 ms | 3.981 ms | 3.867 ms |
| 1000＋1000 | 0.650 ms | 138.986 ms | 138.463 ms |

这是合成大批量新增场景。已有相同 ID 的保存更新会减少实际新增数，普通一条最终回复不等同于此压力。

安全方向是分别扩展内部 guarded merge 的调用范围，而不是直接替换公共函数。必须增加保存更新覆盖、请求/问答关联、乐观消息确认、活动卡片去重、同时间顺序、旧时间字段、异常/无序输入的差分，并重跑完成交接、分屏、选择、滚动、语音自动播放和终态动画。

## 2. 结构事件复制是高置信度的后端候选

当前 `workbench/chat/run_timeline.py:RunTimeline.apply` 仍在结构事件分支前 `copy.deepcopy(self.records)`，最后遍历所有记录比较。文本增量及工具事件已有局部处理，不能说所有 token 都在全量复制。

| 记录数 | 完成一个已有回复 | 单独 deepcopy | 已有回复文本 delta | 权限等待、没有记录内容变化 |
|---:|---:|---:|---:|---:|
| 10 | 0.028 ms | 0.022 ms | 0.0013 ms | 0.024 ms |
| 100 | 0.222 ms | 0.208 ms | 0.0013 ms | 0.217 ms |
| 1000 | 2.137 ms | 2.061 ms | 0.0013 ms | 2.127 ms |
| 5000 | 10.575 ms | 10.249 ms | 0.0014 ms | 10.623 ms |

每项 15 个样本；每条初始正文 2 KiB。深拷贝并不意味着不可变字符串正文按长度复制，这些结果主要体现对象遍历成本。两列是独立调用计时，不能相减当作严格函数分解。

原研究中的 `targeted_done` 有已知去重和协议差异，仍不能合入。较安全的新方案应保留完整 `apply` 入口、payload 合并、eventId 去重、revision 行为及分派，只替换 before-image 和变更检测。首次创建回复会关闭旧活动成员关系；取消、迟到工具、重试 replacement、终结必须收集全部受影响记录，不能用“只找到目标 ID”替代这些规则。

## 3. 关闭日志级别仍支付序列化成本

`core/observability.py:log_operation` 先调用 `_bounded_operation_payload`，执行脱敏、递归转换及 JSON 编码，再调用 `logger.log`。默认日志配置通常为 INFO；DEBUG 操作记录即使最后被过滤，也已经付出这些成本。

标准 `logging.Logger`、普通结构字段、每组 1 万次调用、5 轮交替：原版中位数 80.201 ms；实验性级别守卫 2.726 ms。DEBUG/INFO/ERROR 三种门槛及完成、阻塞、取消、失败、显式日志级别组合中，两个版本各 15 条实际输出完全一致。

这只证明该局部路径有可消除开销，不代表整个 agent 快 29 倍。OperationLog 的时钟、字段收集和异常行为仍需要保留；不要通过关闭现有错误日志或降低可观察性换速度。自定义 logger、运行中日志配置变化及序列化失败的合同仍需补验。本轮没有把原型接入产品。

## 4. 合并变快以后，渲染仍是独立瓶颈

当前生产 WbcTranscript/WbcAssistantMessage、React production、实际 Markdown 和 CSS，在隔离 Chromium 页面中重测。每组 3 次挂载、每次 5 次真实增量更新；每次验证行数及末尾内容。下表来自未插入渲染计数器的运行。

| 历史＋运行记录 | 单独投影 | 初次提交 | 初次提交含布局 | 增量提交 | 增量提交含布局 |
|---|---:|---:|---:|---:|---:|
| 100＋1 | 0.20 ms | 11.70 ms | 20.80 ms | 1.40 ms | 1.70 ms |
| 100＋100 | 0.20 ms | 20.80 ms | 35.60 ms | 4.60 ms | 4.90 ms |
| 1000＋1 | 0.40 ms | 73.70 ms | 156.50 ms | 7.20 ms | 7.90 ms |
| 1000＋1000 | 1.10 ms | 179.60 ms | 336.10 ms | 38.60 ms | 39.80 ms |

另一次只在实验 bundle 插入计数器：每次只更新最后一条消息，四种规模分别执行 101、200、1001、2000 次 WbcAssistantMessage。单纯加快数据合并没有隔离稳定历史组件的更新。

但 Markdown 已有 useMemo，流式稳定块已有 memo，不能因此声称每次都重新解析全部 Markdown。`wbcApplyTimeline` 也已保留未变记录引用：1000 条运行记录的一条 patch 约 0.058 ms，5000 条约 0.291 ms，不是当前首要成本。随后投影仍会创建运行记录对象，需要同时考虑引用稳定性。

建议先做消息引用复用与精确的更新边界，保留完整 DOM。不先采用历史虚拟化、移除隐藏内容、减少动画或增大 48 ms 缓冲间隔。普通 React.memo 不足以保证正确：语言、语音订阅、附件、工具卡片、重试状态、回调和 mutable msg 等依赖都必须列入验证。

这里测的是生产组件隔离页的同步提交和强制布局，不是完整 Workbench 或前台实测 FPS；两次分别测计时和组件次数，避免用插桩时间作为正式基准。

## 5. 终端不是单纯磁盘瓶颈

生产终端基准，单终端 512 × 4096 bytes，共 2 MiB。3 次未插桩样本全部验证：发布字节、持久化字节、回放字节均为 2,097,152。

- 首段发布：0.031–0.040 ms。
- append 合计：3.63–3.96 ms。
- flush 等待：660.82–669.69 ms。
- 随后的屏幕快照等待：1149.37–1162.79 ms。
- 回放：4.21–5.09 ms。

单独剖析实际后台 worker：约 2494 万次函数调用；pyte `screens.draw` 的内部时间约 2.68 秒，`history.IncrementalPlainTextParser.feed` 累计约 1.81 秒。历史解析对 2 MiB 数据调用增量 UTF-8 decode 约 210 万次，每字节一次。带 profiler 的时长有显著额外成本，只用于定位热点，不能与上述正常时长混用或相加。

`flush` 的墙钟含 worker 等待和索引解析，不是纯文件写入时间；屏幕等待也可能含排队，不是严格独立的绘制 CPU 时间。worker 同时拥有滚动记录、SQLite 和屏幕处理，优先级与顺序会影响尾延迟。实际首次输出已经很快，因此不能把 1.8 秒理解为“终端首字显示等 1.8 秒”。

较安全的候选是为 normal 状态、无控制字符、无 UTF-8 待续字节的连续 ASCII 段增加块处理，复杂数据回到原状态机；也可研究批量索引写入。必须逐块比较 parser.state、行文本、startSeq/endSeq、CR/LF、退格、ANSI/OSC、拆分 UTF-8、畸形字节、恢复和搜索结果。屏幕绘制优化不能省略滚动、光标和控制序列语义。

## 6. 调试日志请求会阻塞事件循环

`DebugEventRepository.context_events` 扫描最多 20 个文件的全部 JSONL 后才排序截取；`http/system/events.py` 的 async 路由直接调用它。返回 limit=120 不意味着只读取 120 条。

合成日志每条包含约 1 KiB 消息内容，另有损坏行；直接执行与 `asyncio.to_thread` 对照，返回结果哈希一致：

| 记录数 | 同步查询墙钟范围 | 同步时 heartbeat 最大延迟 | 线程化时最大延迟 |
|---:|---:|---:|---:|
| 1000 | 2.5 ms | 2.6 ms | 0.6–0.8 ms |
| 10000 | 25.0–25.5 ms | 25.1–25.5 ms | 0.4–10.4 ms |
| 50000 | 146.0–146.8 ms | 146.2–146.9 ms | 13.1–16.1 ms |

线程化样例总耗时没有明显减少，甚至更高；它主要减少事件循环独占，并不消除 JSON CPU 或 GIL 竞争。这里是同一异步循环内调用仓库函数的实验，不包含真实 HTTP 压力测试。该影响以实际请求调试列表为条件，不应解释成每次普通聊天必然发生。

第一步可隔离同步读取；第二步再做文件身份/大小/偏移索引。轮转、截断、损坏行、文件删除、重复 ID 覆盖顺序、返回排序和详情必须保持。

## 7. 存储初始化检查可用更精确的查询结构

`ContextTreeStore.__init__` 每次执行缺失 token 计数检查。EXPLAIN QUERY PLAN 确认正常无缺失时扫描 context_nodes。

| 节点数 | 原缺失检查 | 临时部分索引后 | 原打开总耗时 | 索引后打开 |
|---:|---:|---:|---:|---:|
| 1000 | 0.022 ms | 0.001 ms | 0.219 ms | 0.139 ms |
| 10000 | 0.465 ms | 0.001 ms | 0.673 ms | 0.148 ms |
| 100000 | 5.998 ms | 0.001 ms | 6.452 ms | 0.290 ms |

实验索引：`ON context_nodes(node_id) WHERE self_token_count IS NULL OR path_token_count IS NULL`。仅在一次性数据库创建，产品 schema 未改。注入缺失值后仍可查出，并由生产打开路径完成 backfill。

这是内存文件系统、已有合成数据库的测量，不包含首次创建索引成本、真实冷盘、所有写入负载和迁移竞争。索引比“进程内标记已初始化便永久跳过检查”更有希望保持外部写入检测，但仍需旧库、事务、写放大和恢复回归。

## 8. 连接复用应降低优先级，确定关闭仍值得做

每组 200 次独立 append 事务，3 轮交替 current/显式 close/同线程复用；事件 seq 和 event_json 哈希完全一致，均未改变同步级别或事务批量。

| 存储位置 | 当前连接方式 | 显式关闭 | 同线程复用 |
|---|---:|---:|---:|
| /tmp，tmpfs | 12.86 ms | 11.48 ms | 4.10 ms |
| 仓库临时目录，ext4/NVMe | 366.59 ms | 355.47 ms | 335.76 ms |

真实磁盘样本的复用下降约 8.4%，远小于内存盘倍率。默认 journal_mode=delete、synchronous=2 保持一致；没有降低持久化承诺。

当前方式结束 200 次调用后仍有 17 个该数据库文件描述符，强制 GC 后归零；显式关闭为 0，复用为 1。说明连接释放依赖 GC，**不是已经证明永久 FD 泄漏**。原型复用仅用于单线程，没有证明线程所有权、锁冲突、回滚、取消线程继续提交、数据库文件替换和关闭恢复的等价性。先修明确生命周期比直接全局连接池更稳妥。

## 9. 缓存的全局锁是真问题机制，不等于已证明主因

8 个不同 SQLite 数据库各含 1000 条记录：并发冷读总计约 18.64 ms；8 次顺序热读中位数 1.31 ms；只实际加载 8 次，返回副本隔离通过。

独立控制实验让一个 cache miss 的 loader 固定 sleep 50 ms，此时另一个已经缓存的 key 仍等待 50.44–50.71 ms。证明全局 RLock 把无关 key 的加载/命中串行化；**50 ms 是人为条件，不是用户数据的实测 miss 分布**。

该缓存主要属于 Workbench 上下文读取，不是 AgentSession._prepare_model_input 的通用缓存。不得把拆锁直接说成模型输入准备加速。优化时仍需同 key single-flight、连接租借/淘汰安全、WAL data_version 前后校验、inode 替换、插件 owner 依赖、大小上限及返回副本；Python CPU 型 loader 也未必因线程增加而提高吞吐。

## 10. 真实 AgentSession：并发与历史增长仍存在

重新运行真实 AgentSession 合成矩阵，固定模型每次等待 10 ms，工具 8 KiB；1 次当前版本矩阵，不宣称本轮三次统计。累计 19 个会话、92 轮、14,100 个流式分片；模型/工具调用数、顺序、最终正文、idle 和正常关闭后恢复全部通过。

| 会话 × 每会话轮数 | 单轮工具/分片 | 总时间 | 单轮中位数 | 准备输入中位数 | 主循环 lag p95 |
|---|---|---:|---:|---:|---:|
| 1 × 3 | 5 / 100 | 424.71 ms | 140.75 ms | 10.42 ms | 3.02 ms |
| 4 × 3 | 5 / 100 | 897.87 ms | 305.05 ms | 30.65 ms | 4.03 ms |
| 12 × 3 | 5 / 100 | 2948.71 ms | 916.75 ms | 129.81 ms | 20.44 ms |
| 1 × 40 | 1 / 100 | 2397.45 ms | 60.84 ms | 5.26 ms | 6.62 ms |
| 1 × 1 | 5 / 5000 | 282.91 ms | 282.61 ms | 7.25 ms | 5.14 ms |

40 轮前五轮/后五轮中位数：总时长 45.09 → 72.55 ms，输入准备 2.32 → 7.86 ms。单独剖析 80 次准备调用，发现上下文投影、task 投影、deepcopy、日志序列化及 token 估算都有成本。调用链包含重入与嵌套，不能把累计时间各行相加；这不是已完成输入阶段全部开销的独立因果分解。

可研究基于真实版本/依赖的上下文投影和工具 schema 复用，但任务切换、权限、插件注册、模型路由、retry correction、上下文修改、压缩和恢复会失效。不能以丢历史、减少工具定义或修改模型参数为优化方式。现有 HTTP 客户端池、增量事件、落盘批处理和流式稳定块优化都已经存在，不应重复立项。

## 修复顺序与无功能变化验收

1. **保存/旧协议合并、日志级别守卫**：两项独立提交，前者复用严格输入守卫，后者保证所有实际启用的日志内容与级别不变。
2. **后端结构事件**：保留原分派，只优化受影响记录捕获。逐事件比 patch、snapshot、revision、seen、映射和持久化恢复，不能复用已知不等价旧原型。
3. **稳定历史组件更新**：先保证数据引用和依赖完整，再精确 memo；保留所有 DOM 与现有动画时序。对照 Markdown、选区、编辑、语音、工具卡片、主题/语言、分屏、导航、重连及动画。
4. **终端、日志扫描、存储索引**：分开推进；解析状态/字节位置、日志轮转、迁移和写入语义各有独立门槛。
5. **连接和缓存并发**：以真实争用与冷盘分布排序；明确资源所有权后再修改。
6. **上下文跨轮缓存**：最后做依赖失效设计，不能用 TTL 或仅 mtime 代替正确性。

本轮不把任何新原型标记为“已经安全可合入”。研究提供了触发条件、收益上限线索与验收合同，没有承诺任意设备上的整体加速百分比。
