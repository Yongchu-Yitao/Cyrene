# 子 Agent 无进展检测：行为与性能核查

日期：2026-09-20。基于当前本地工作区。只增加本实验文件，不修改产品实现。

后续实施说明：用户随后要求彻底移除该功能，执行型无进展检测现已删除。下文和 `results.json` 是删除前的实验记录；原探测源码以 `probe.pre-removal.py.txt` 归档，不适用于移除后的 API。替代回归验证位于 `tests/test_subagent_execution_limits.py`。

## 结论

它能识别精确重复以及 A/B 结果循环，具有有限止损价值。但当前实现把内容新颖度近似为工作进展，并据此硬阻断后续工具。已复现正常工具发现导致任务提前终止，因此不能视为可靠的通用无进展判断。

性能开销主要来自同步重写整个子 Agent 管理状态；单次摘要计算通常较便宜。现有证据不足以断言它是全应用主要瓶颈，也不足以证明其节省的模型费用超过误停和维护成本。

## P1：正常工具发现三轮后被误判并阻断执行

完整 AgentSession 实验的子 Agent 依次执行：

1. `toolbox.list`：成功，计数变成 1。
2. `toolbox.describe(SearchOne)`：成功，计数变成 2。
3. `toolbox.describe(SearchTwo)`：成功，计数变成 3，标记 `execution_no_progress`。
4. `toolbox.invoke(SearchOne)`：内层搜索被拒绝，真实搜索函数执行次数为 0。
5. 子 Agent 报告 blocked 并 quit，最终状态为 incomplete。

每轮确实取得了新的工具信息，却被记为无进展。并不是模拟工具批次计数造成的假象：完整实验由真实 AgentSession 自动发出 `tools.completed` 事件。

原因：

- `core/plugin/runtime.py::_dispatches_own_tool_hooks` 对 toolbox 不发自身工具 Hook，invoke 时由目标工具处理 Hook。这一设计避免重复处理包装层，本身有合理性。
- `toolbox.list/describe` 没有调用内层目标工具，因此没有 PostToolUse 进展记录。
- `cyrene_subagent/manager.py::_on_child_event` 对每次 `tools.completed` 都读取 `_tool_batch_progress.pop(id, False)`。没有观察记录被直接解释为“没有进展”。

这证明的是“未知进展”和“确认无进展”混淆导致误停，不意味着每次工具发现都会失败；标准 list → describe → invoke 的两轮发现一般还未达到默认阈值。

## 判定算法的有效范围

| 场景 | 实测结果 | 解释 |
|---|---|---|
| 同一文件同一结果，四个单工具批次 | 计数 0、1、2、3，触发 | 能阻止明显重复读取 |
| 观察结果 A、B、A、B、A | 计数 0、0、1、2、3，触发 | 能阻止有限结果集合内的循环 |
| 相同失败但时间戳每次变化，八批 | 始终 0 | 仅这项检测无法识别无关动态字段 |
| 相同失败，非观察类调用参数每次变化，八批 | 始终 0 | 新调用签名足以算进展，不要求成功 |
| 合法轮询，固定返回 running，四批 | 触发 | 正常等待可能被误停 |
| 四个不同文件，内容都为 TODO | 触发 | 观察结果不绑定资源身份 |
| 不同查询均返回 no matches | 触发 | 排除不同假设的工作可能被误判 |
| 每批重复工作附带一项新内容 | 始终 0 | 单个新指纹重置整批计数 |
| Python 缩进改变，非空白字符相同 | 第二个结果被当成重复 | 合并空白会丢失某些语言的语义差异 |

除完整工具发现场景外，上表是现有检测函数的隔离测试。模型、工具失败熔断、超时和费用上限可能独立结束真实任务，因此不能将“该检测没触发”说成“整个 Cyrene 一定无限循环”。

此外，结果取 `str(value or error or "")`，既不按工具输出结构规范化，也不检查 success。观察类工具根据名称子串识别，而不是根据工具元数据。

## 收尾是硬限制，不是自动换策略

一旦设置 finalization_reason，普通工具在 PreToolUse 被拦截，只允许 quit；运行时提示提交 partial 或 blocked。已有结果可交回主 Agent。本实验完整链最终正确交回 blocked。

检测器本身不调用 DeepReflect、不重规划、不撤销文件修改。其负面判断影响较大：错误判断会在子 Agent 真正开始工作前关闭执行路径。

## 恢复边界

签名、指纹和计数持久化，但当前批次“是否已有新信息”的 `_tool_batch_progress` 只在内存。

隔离实验模拟 PostToolUse 已记录新信息之后、批次完成之前恢复：恢复后的批次被记为一次无进展。本实验仅确认状态结构和批次结算问题，未做真实进程崩溃注入；不能宣称所有重启都会发生此问题。

## 性能实验

本机合成微基准，真实 ContextStoreRouter/SQLite，默认 token counter，关闭日志。记录状态中预填历史指纹。测试数据与线上真实会话大小不同，结果不是应用耗时百分比。

### 单次记录结果并完成一批

每项预热 5 次，记录 40 次，以下为中位数：

| 返回内容大小 | 管理状态中的子 Agent 数 | 关闭持久化 | 开启真实持久化 |
|---|---:|---:|---:|
| 约 1 KiB | 1 | 0.037 ms | 2.906 ms |
| 约 1 KiB | 8 | 0.038 ms | 28.483 ms |
| 约 1 MiB | 1 | 4.965 ms | 8.123 ms |
| 约 1 MiB | 8 | 5.012 ms | 33.870 ms |

“关闭持久化”仍含参数序列化、结果空白处理和摘要、历史列表查询、指标与默认设置读取。设置使用测试替身，因此不是纯哈希性能测量。

“开启持久化”包括每次结果与批次结算各一次全状态保存。实际 AgentSession 还有状态和模型事件，其总成本未包含在这个微基准中。

### 同样保存整个管理状态，仅改变指纹历史是否存在

每项预热 5 次，记录 60 次；有历史时每个 Agent 各 200 条调用签名和 200 条结果指纹。

| 子 Agent 数 | 无指纹历史：单次保存 | 有指纹历史：单次保存 | 根节点 JSON 大小变化 |
|---|---:|---:|---:|
| 1 | 0.660 ms | 1.415 ms | 约 2 KB → 29 KB |
| 8 | 3.090 ms | 14.970 ms | 约 14 KB → 232 KB |

这组 A/B 保留同一持久化方法，避免把所有子 Agent 状态维护开销都归罪于无进展检测。当前指纹历史确实放大每次全量保存的开销；不是多出 12 ms 的哈希运算。

源码路径：`record_tool_result` → `_persist` → 全部 records/public snapshot 组装及深拷贝 → 主树根节点 `update_node` → 编码/计数/SQLite 事务/变更发布。整个过程在 manager 锁下同步执行。

内存列表仅 append，持久化时才截取最近 256 项；内存查找仍为列表线性查询。默认 200 工具预算限制了常规单次执行规模，但恢复或重新激活与更高配置下仍应注意这一区别。

## 测试覆盖判断

之前通过的 188 项定向测试包含子 Agent 模式、通信、完成证据等，但当时并没有证明这项无进展算法能正确区分正常探索和死循环。

本次搜索 `no_progress`、`execution_no_progress` 等未发现现有 tests 中针对该算法的专门断言。此次新增的完整会话实验补出了“正常发现工具被误停”的具体反例。

## 建议

1. 优先修正未知进展被记成无进展的错误，纳入真实会话回归测试。
2. 当前信号不宜默认直接终止子任务。可以作为提醒或复查信号；只有更明确的重复证据才进行硬限制。
3. 保留耗时、工具次数、费用等独立资源限制；它们与语义进展判断是不同职责。
4. 若继续使用指纹，需区分工具语义、资源身份、正常等待、失败类型和动态元数据，而不是统一全文空白归一化。
5. 减少全管理器状态的同步写入，采用有界集合、按变化更新和明确的批次持久化边界。
6. 在没有真实任务误停率、死循环拦截率和节省成本数据之前，不宣称它已证明有正收益。
