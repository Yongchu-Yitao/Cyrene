扫描 src 的全部 Python 作用域以及现有分析器收录的 WebUI/Electron JavaScript 作用域；阅读热点的职责、调用与资源边界，抽查相应测试。复用上一轮对 Send、恢复、提交和取消的深入分析。这是全项目静态扫描加热点审读，不是逐行审完每个插件，也不是一次新的功能验收。

该提交的 GitHub CI 已通过：Python 2762 通过、2 跳过，WebUI 116 通过，Electron 127 通过。这说明当前测试集通过，不证明任意重构都安全。本轮未改业务代码、未删除测试、未修改预算，也没有重复运行测试。

**最值得先做：模型配置规范化、Send 准备阶段合同。** 随后处理状态恢复决策与消息投影，再推进前端交互所有权。终端线程、会话锁、跨平台原生窗口和供应商传输机制放在后面专项处理。

排序依据是可确认的职责问题、修改影响、可独立实施程度与验证成本，不是把复杂度数值直接变成“收益分数”。性能采用用户确认的取舍：维护收益可以优先于微小开销，但仍保留交互、背压、吞吐和资源释放合同。

## 1. 模型配置：性价比最高的确定性边界

位置：`src/cyrene/plugins/builtin/cyrene_model/configuration.py:140`。

现在一个函数同时验证文档、迁移连接、规范化连接、恢复旧密钥、建立 profile、解析角色路由。已有 `_identifier`、`_context_limit`、`_capabilities`，无需另建 schema 框架。

建议保留顶层顺序，抽出连接、profile、route 三类结果构造。对跨项引用与重复 ID 校验留在集合层，单条记录校验放到对应函数。连接的“空密钥保留旧值”“明确清除”“非 API key adapter 清空”三种语义必须保持；Codex/local ONNX 的地址差异、旧版本迁移、ctx 等兼容字段也不能顺手移除。

`platform/settings_service.py:278` 的快捷键分支包含独立循环与校验，可以先独立出来。保持 bool 不能当 integer、非有限浮点拒绝、空快捷键/None 的区别及错误次序。不把模型连接资源塞进现有标量 SettingSpec，也不为两个领域建立万能 validator。

完成标准：新增一类 profile 规则只需修改所属解析器；同输入得到同结果和同首个错误；不改变 secret 公开读 API、缓存失效和持久化路径。已有 test_model_configuration.py 可作为行为对照基础。

## 2–4. 后端运行链：按准备、恢复、提交拆开

详细合同见 backend-next-complexity-research-2026-09-07.zh-CN.md。

Send 的问题是命令、正文、附件随阶段被覆盖，而不是 execute 中清晰的串行顺序。建立明确准备结果，比继续把字段包装成小对象更有价值。重试必须从历史用户消息恢复输入，普通发送使用请求；不能当作重复分支删除。第一刀保持工作流启动、落盘、回滚、附件注册和标题任务先后顺序。

恢复先分离决定“下一步是什么”的代码，保留原 store 查询与状态发布次序。取消、待用户、上下文压缩/反思、工具批次和 SessionEnd 都是独立功能。已有 TransitionDriver 不需要再提取一遍。

`workbench/core_adapter/bridge.py:390` 的工具活动卡投影同时扫描终态 run、建立结果索引、归并调用并形成持久化卡片；`:614` 将实时事件投影成前端事件。可以共享经验证相同的单条卡片字段构造，但持久化恢复与实时流事件不是同一种输入，不能强制走一条热路径或每个 token 重投影整棵树。

提交仍使用现有 ConversationTurnCommit、repository/outbox 和 finalization 服务。Send、Answer、外部回复、后台唤醒的计数、pending、通知、retry 截断有所不同。先统一模型/用量/标识字段的投影，不增加布尔参数密集的万能 finalize。

保留恢复不重复执行、取消与提交串行化、消息/outbox 原子写入、pending 身份、历史工具卡去重测试。这些不是无意义测试。

## 5. Rail / Topbar：按完整交互职责分离

位置：`frontend/features/chat/rail.jsx:69`、`frontend/features/shell/topbar.jsx:93`（均位于 webui 下）。

Rail 同时处理项目工具视图持久化、插件可见性、集合加载/错误、聊天分组、终端与拖动。上一轮分组投影已经简化，下一步不应再提出相同索引优化。优先抽出插件集合的加载与失效所有者，让组件接收数据和语义动作；保持项目切换、插件关闭、加载失败、展开状态、拖动和条目身份。

Topbar 的菜单、悬停预览、延迟关闭 timer、异步资源序号与定位监听器仍集中。将会话菜单/预览作为完整生命周期拆开，比只拆菜单 JSX 更有维护价值。宽度测量已用 ResizeObserver 和 rAF，有清理逻辑；不能仅因订阅数量多就认定泄漏。避免为每个 tab 新增订阅或截图请求。

验收要包含快速切换菜单时旧响应不覆盖新菜单、移出关闭/重新进入、溢出区拖动、固定排序、缩放后定位。保留 DOM key、焦点和滚动位置。

## 6. 聊天页与 Composer：剩余复杂度并未靠 Hook 拆分消失

页面仍有 126 个直接 Hook，Composer 有 51 个；这只是定位线索。上一轮已经集中分屏选择和输入设置，不重复实施。

下一步先梳理 chat-owned、project-owned、floating、detached 面板的归属和恢复合同。通过语义操作管理“打开/移交/关闭/恢复”，不合并用途不同的布局宽度、列表选中与实际分屏。需要核对 pane-layout-controller、pane-content 和浮动浏览器展示的共同事实，现阶段没有证据支持直接统一成一个状态容器。

Composer 的高决策数有大量 JSX 条件。可按附件交互、命令/上下文选择、发送意图建立边界；必须保留 IME、快捷聊天命名空间、编辑焦点、附件失败恢复和运行中指导。拆展示可提升阅读性，但不应宣称聚合逻辑减少。

## 7. 供应商适配：不要把协议差异当垃圾复杂度

`model/codex_provider.py:1024` 的 complete 同时协调 thread/turn、通知 task、首信号与总超时、interrupt、事件累积和 action envelope 转换。先抽事件累积结果，保持通知等待、两个超时边界、取消和 finally 清理的所有者；不要改变 Cyrene 工具循环的权威地位。这是源码审查，未对外部 Codex 产品协议做新版本验证。

MiniMax 视频将恢复任务、V1/V2、素材分类、提交、轮询与结果处理集中；已落盘的 api_version 在恢复时优先，这属于兼容合同。Google 视频存在 Veo/Omni 等差异。可分别提取每个版本的请求构造和响应解析，保留素材角色限制与错误码，不先抽跨供应商万能轮询器。

这些方向需要事件/HTTP 录制回放及超时、取消、恢复验证，优先级低于确定性的配置处理。

## 8. 终端、Electron：先画清资源边界再动

终端 `_TerminalPersistenceWriter` 已集中 scrollback 分段、SQLite、screen 解析和查询，并有主队列/查询队列及两个线程。下一步可分离分段存储算法、查询 SQL/投影与 screen 处理，不改变工作线程数、优先级、每终端公平调度和 flush token。方法数量包含查询和诊断方法，不等于全部都是职责错误。

已有测试覆盖阻塞历史查询不延迟屏幕处理、多个高输出终端的公平调度、分段回收等待读者、跨 flush 的 marker 和旧数据序号。应保留，并用既有终端性能基准检查重构是否真正执行了改动路径。

Electron 选择器已抽出；下一块是 main.js:1598 起的全屏进入、窗口挂载、尺寸同步、退出和监听器清理。代码存在独立视频窗和主窗全屏不同路径，不能仅用 macOS 通过证明所有平台等价。也不应改变 partition、共享登录或 webContents 身份来方便拆分。
