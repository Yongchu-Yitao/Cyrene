# Cyrene 保持完整功能的性能优化研究

> **严格复核后的状态（同日更新）：当前没有任何原型获得“全功能等价、可合入”的结论。** 前端原型存在稀疏数组反例，后端计时原型存在多项协议语义差异。下文性能结果仅用于定位成本；实施顺序是研究优先级，不是安全合入许可。详见 [严格等价复核](performance-equivalence-recheck-2026-09-20.zh-CN.md)。

研究日期：2026-09-20。基于当前工作区，HEAD 为 `8806c588ae662970392a0af0e9e18ce66aa26df5`；工作区存在其他修改，研究过程中也有其他文件变化。本次只新增研究文档、实验脚本和结果，没有修改产品代码。

## 结论

最值得先做的是**前端时间线合并算法**，其次是**后端结构性事件的全量复制**。这两项可以减少重复计算，无需减少历史、工具、上下文、模型能力或持久化保证。已用当前源码和隔离原型测出可复现的局部收益；尚未证明真实应用的端到端收益，也不能仅凭这些样例证明所有功能完全等价。

数据库连接生命周期、上下文缓存并发和调试日志查询是第二批候选。先测量再改，不建议为了速度调整模型、降低生成质量、截断历史、跳过权限审查、丢弃事件或放宽落盘语义。

## 已有优化：不应重复立项

- `run_timeline.py` 已有单条文本追加补丁，工具事件也走局部变更路径；问题主要留在其他结构性事件。
- `chat_runs.py` 已把事件落盘移到线程并批处理，当前流式批量窗口为 1 秒、上限 512 条；应保持当前恢复语义，不靠继续加大窗口制造收益。
- `context_read_cache.py` 已有有界缓存、WAL 提交感知、插件归属依赖失效和返回副本。
- 模型请求已有 `model_http_clients` 池，按连接、凭据摘要、代理、超时等隔离；不应再笼统建议“复用 HTTP 连接”。
- 前端构建已有代码拆分、压缩；终端已有分段滚动记录、后台写入和查询线程。

## P0：把消息合并的平方增长改成线性处理

源码：`src/cyrene/workbench/webui/frontend/features/chat/runtime-timeline.jsx` 的 `wbcMergeChronologicalMessages`、`wbcProjectTranscript`，调用处为 `conversation.jsx` 的消息投影。

当前每插入一条新增消息，都从头扫描 `merged`，反复 `Date.parse` 并执行插入。对 N 条历史和 M 条新增记录，最坏工作量约为 **O(NM + M²)**。时间线每次变化又触发投影，长运行会放大开销。这里的 M 是当前运行中的记录数，不等于 token 数；普通只有一条活动回复的会话不会达到相同压力。

实验将当前 JSX 转换后在 Node VM 中执行纯函数，不含 DOM、React commit、网络或模型。原型也在同类 VM 中执行。每项预热 3 次、采样 10 次；下面是中位数，单位 ms。

| 历史条数／运行条数 | 原投影 | 线性合并原型 |
|---|---:|---:|
| 1000／1000 | 448.56 | 1.20 |
| 2000／2000 | 1800.31 | 2.28 |

对照：2000 条历史＋1 条运行记录的原投影约 1.04 ms。不能把压力场景的倍数写成“Cyrene 整体快几百倍”。Node VM 的绝对时间也不能代替 Electron 页面实测。

**可实施方案：**预解析时间；对时间有效、有序且没有特殊关联处理的两个序列使用稳定的双指针合并；复杂情况保留原算法。维护 id 去重，等时间时保留原先的插入顺序。随后再考虑跨增量复用投影结果，减少稳定历史的重复扫描。

原型通过 200 组确定性输入的原算法输出对比，以及四种规模的完整投影对比。覆盖部分重复 id、同时间、倒序、无效日期、clientRequestId 回退；这不是完整兼容性证明。原型仅在 `frontend_probe.mjs` 中。

**合入门槛：**补齐 pending-question 回答关联、乐观消息确认、用户插话、不同 id 的同一工具卡片、更新版本 checkpoint、旧协议、重连恢复、未知时间和空 id；验证输入没有被原地修改。直接用生产原函数作差分 oracle，增加真实事件录制回放。保留所有消息 DOM 时，查找、选择复制、导航和无障碍行为更容易保持；本轮不需要先引入历史虚拟化。

## P1：结构性事件只复制、比较受影响记录

源码：`src/cyrene/workbench/chat/run_timeline.py:212`。

文本 delta 和工具事件已绕过全量副本；但回复完成、开始、通知等路径仍先 `copy.deepcopy(self.records)`，再遍历全部记录判断变化。即使只完成一条已知回复，也支付整个运行的复制成本。

隔离实验使用每条含 2 KiB 文本的时间线，处理一条有明确 messageId 的回复完成事件，采样 50 次：

| 运行记录数 | 原实现中位数 ms | 只更新目标记录的原型 ms |
|---|---:|---:|
| 10 | 0.027 | 0.0032 |
| 100 | 0.227 | 0.0032 |
| 1000 | 2.238 | 0.0032 |
| 5000 | 11.229 | 0.0031 |

每种规模对第一次事件验证返回 patch 和完整对象状态相同。原型只验证“已存在且明确标识的回复完成”这一条路径，没有实现事件去重、未知来源创建、重复完成等完整入口语义，不能直接替换 `apply`。

**可实施方案：**让各事件分支显式收集 touched records；修改前只保存这些记录所需的比较信息，保持 revision、去重和无变化事件行为。结束整个 run 时确实需要遍历未完成记录，不能省略状态收尾。创建回复时关闭旧活动成员关系，也必须保留。

**合入门槛：**针对整段事件流逐事件比较旧、新 patch、snapshot、最终持久化消息；覆盖迟到工具结果、重复事件、取消、失败、用户插话、权限等待和终结事件。测 p95 事件循环阻塞，而不只看微基准。

## P2：有代码依据、收益尚待测量的候选

| 候选 | 当前证据 | 保持功能的做法及边界 |
|---|---|---|
| 事件库连接复用与确定关闭 | `ChatRunEventStore._connect/append_many` 每次操作新建连接；24 会话测试第三个样本记录 392 次事件库连接 | 用有明确所有权的数据库 worker 复用连接。`with connection` 管事务，不负责关闭连接；需要显式关闭或受控生命周期。保持事务边界、重试、去重、终结落盘、恢复顺序；不改变 synchronous 保证 |
| 上下文缓存锁粒度 | `ContextReadCache.read` 的一个全局 RLock 覆盖 `load`、序列化和反序列化，不同树的 miss 也串行 | 短时全局 LRU 锁＋每 key 的加载合并；连接需要租借/引用计数，避免淘汰关闭正在使用的连接。保留 data_version 前后校验、替换文件识别、插件归属依赖、内存上限及副本隔离 |

| 上下文存储重复初始化检查 | 打开 `ContextTreeStore` 时检查 schema，并查询是否存在空 token 计数；无缺失记录时可能扫描节点表 | 用迁移版本和可靠的完整性标记，或经 EXPLAIN/大库实测选择部分索引。必须支持旧库、恢复、外部写入与原有计数语义 |

连接数来自基准最后一个样本，不是三个样本的中位数；它证明存在连接 churn，不证明它是当前最大延迟来源。缓存锁及日志路径也是源码层面的候选，未量化真实用户负载下的收益。

## 当前基线与验证边界

隔离 `CYRENE_BASE_DIR`，使用临时数据库和固定模型/工具结果；没有真实模型或网络请求。最终 chat 和 search 各重复 3 次并正常退出。

| 场景 | 并行会话 × 轮次 | 指标 | ms | 内容校验 |
|---|---:|---|---:|---|
| single_heavy_run | 2 × 3 | 每次样本 run p95 的中位数 | 74.587 | 通过 |
| dense_concurrency | 24 × 3 | 同上 | 446.948 | 通过 |
| multi_tool_storm | 12 × 3 | 同上 | 751.605 | 通过 |
| search | 6 × 3 | 整个多会话多轮工作负载总时间中位数 | 213.888 | 通过 |

聊天校验涵盖流式事件、落盘事件、工具结果和遥测数量。search 含每轮 10 ms 搜索＋60 ms 并行抓取的模拟等待，三轮本身就约 210 ms，不能把全部 214 ms 当作本地可消除开销。报告中的 ideal cache 是理论 fixture 复用率，不是真实缓存命中率。

现有 chat 基准没有覆盖完整 AgentSession 模型执行路径、真实插件启动或前端。功能级 suite 的终端场景运行在 45 秒诊断上限内未完成，未获得完整 features 报告；不能声称全功能性能基准通过。一次未隔离的数据配置导入触发了用户目录只读错误，后续改用临时配置目录，不需要访问真实凭据。

首次未隔离 chat 运行虽生成质量通过的报告，但卡在 asyncio 关闭阶段并被诊断超时终止。最终隔离三次重复运行正常退出；诊断曾观测到等待默认 executor 关闭，根因未确认，不能据此认定产品存在关闭死锁。初次全组运行因长时间无输出手动终止，没有有效全组结果。

验证情况：

- 现有前端 `runtime-timeline.test.mjs`：直接执行时 8/8 通过。运行器同时输出 stream fd 权限警告，未把这次结果外推为浏览器验证。
- Python 时间线与缓存的聚焦回归：25 通过，明确排除 1 项此前超时的 live checkpoint 集成测试。
- 首次 Python 组合测试在该 live checkpoint 用例达到 20 秒超时，后续 HTTP 客户端测试未完成；没有宣称整个组合测试通过。
- 未测 Windows、macOS、Android、真实模型首 token、页面帧耗时、启动 RSS、长时间 soak 和断电恢复。

## 建议实施顺序与验收合同

1. 单独实现前端稳定线性合并，扩展差分回放和浏览器长运行测量；这是目前证据最强的优先项。
2. 单独实现后端 touched-record 投影，用完全相同事件流检验每个 patch 和持久化结果。
3. 给完整 AgentSession 的准备、上下文读取、请求发送、首 delta、DOM 首次更新、终结落盘分别计时，再决定数据库/缓存优化的先后。
4. 修复或解释终端基准和 live checkpoint 测试的超时后，完成相同机器、相同数据、交替顺序的 A/B 回归。

“完全不牺牲功能”的验收应落实到：相同模型和参数、相同有序上下文与工具 schema、相同权限流程和副作用顺序、事件不丢不重、恢复后相同消息、错误/取消语义一致、历史与附件可访问、搜索/复制/导航/无障碍不回退。缓存必须检测真实依赖变化，不能仅用 TTL 或 mtime 宣称等价。

固定输入下同时比较 CPU、峰值 RSS、事件循环延迟、前端长任务、首段显示、完整回复和持久化结束。优化前后交替执行并报告分布；只有输出等价和尾延迟均达标才接受。未做正式端到端 A/B 之前，不给整个产品承诺百分比加速。
