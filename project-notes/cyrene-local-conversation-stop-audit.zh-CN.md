### 2. 表面像“承诺后停止”，实际为模型响应失败

用户 ordinal 191、242 分别说“继续”。之前可见文本分别是“重新生成工具调用 — 重写 player.js”和“Write 调用 JSON 不合法……重新生成完整的工具调用”。

| --- | --- | --- |

两者均记录 `failure_kind=model_response_invalid`、`retryable=true`、`retry_scope=different_arguments`，错误文本为模型服务返回无效或空响应。

因此不能把这两例算成正常结束条件误判。优先排查无效工具参数恢复为何最终失败，以及终结错误在消息流中的展示。仅凭这些字段，不能断定供应商具体为何产生无效响应、是否达到输出上限或哪个重试环节失效。

## 对方案的修正

不能统一使用“最后一句像进度汇报 → 自动继续”。应先按底层终结原因分流：

1. **completed/end_turn，但还有已授权义务**：完成检查器识别具体遗漏，继续可执行的下一步。9 月 6 日反复要求用户决定后续实现，是直接回归样本。
2. **failed/model_response_invalid**：走有界参数纠错/恢复，并清晰展示失败原因。不能把它当成功，也不能只提示“继续”而不解决格式问题。
3. **等待输入、取消、记录缺失**：分别处理；证据不足时维持未分类。

这次没有在真实记录中确证“length 纯文本被标成功”是用户遇到的原因；此前源码模拟说明该路径存在，但不能替代真实事故证据。

## 追加核查：纠错失败与“说要做就结束”

### 两次失败已确认重试耗尽

两次 run 的触发节点都保留 `_model_response_retry`：`attempts=1, limit=1, retry_scope=different_arguments`，之后挂载 failed 终结节点。因此并非没有重试，而是当时的一次纠错未能恢复。

第二次 run 内还存在一次早先成功恢复的纠错：Write 参数 `invalid_json`，原始参数长度 12427，随后又有正常工具节点；最后另一个触发节点的 Write 参数为 `invalid_json`，长度 11459，纠错一次后失败。这里的长度是整个参数字符串，不是 Write.content 长度，不能据此直接判定违反 8000 字符内容限制。

纠错提示已经包含“不要只解释错误，重新生成完整工具调用”“Write 分块、overwrite 后 append”等要求。这说明仅增加一句要求继续的提示不能保证恢复。当前 checkout 的 `_MODEL_RESPONSE_INVALID_RETRY_LIMIT` 已变为 3，并处理更多错误类别；本次未改该代码，历史的一次重试上限不能当成当前代码现状。

### 失败投递存在，消息状态有不一致

- 第一次 run 的 durable event seq 313 是 `run.failed`，seq 317 是 `error`。
- 第二次 run 的 seq 779 是 `run.failed`，seq 783 是 `error`。
- 两次 `workbench_chat_runs` 均为 `status=error, termination_reason=agent_error`。
- 第一次可见残留消息 ordinal 190（“重新生成工具调用……”）却标成 `status=completed`；同轮模型状态卡的内层 `modelStatus.status=failed`。
- 第二次残留消息 ordinal 241 标为 `failed`。

因此需要排查消息结算与 run 状态一致性，不能声称后端完全没发错误；没有复现当时 UI，不能确认用户当时实际看到了什么。

### “tilemap.js……修：”已排除自行停止

`run_cf49a1746a0f46549458a1f61c8ef08a` 的 ordinal 614 是这句话，但 615 紧接着有真实 Edit 调用，状态 failed。随后 run 的最终状态为 `cancelled/user_interrupted`，seq 1166 的 `run.cancelled` 时间为 `2026-09-06T11:40:31.016516+00:00`，引用执行 run `run_1652cdf7249a471b9d0183259f8af82b`。不能只根据正文消息的 completed 状态判断整轮自行完成；也不能仅凭 user_interrupted 判定是哪一个 UI 操作触发。

### 有没有其他“承诺执行后终止”

历史 PDF 加图记录仍是可见层面的候选：“现在我来下载图片并加入文档。”之后用户说“继续”，下一轮才出现改写/编译/交付。但缺少对应旧 run 的终止原因，只能证明对话边界，不能证明自主正常停止。PPT 例继续不计入确定样本。

本次对两版当前 ContextTree 的 completed 终结节点及短文本承诺候选做了筛查，未找到另一个足够确证的“承诺具体动作、无后续工具、正常自主终结”案例。关键词筛查不完备，不能据此断言从未发生。已确证的正常提前收尾仍是将已授权的后续实现重新交给用户选择，与本节更狭义的“承诺后立即终止”不同。
