# 下一阶段复杂度治理研究

研究基于 2026-09-07 当前工作区（main，包含尚未提交的 composer、刷新和 page-state 重构）。本轮重新运行静态指标采集并阅读重点实现，没有修改产品代码、预算或执行测试。指标不是运行时性能结论。

## 判断标准

下一阶段不以 Hook 数、文件长度或文件数量作为主要成果。要求减少以下至少一项：同一事实的可变副本、一次业务操作需要协调的写入口、依赖隐式调用顺序才成立的中间状态、资源创建与清理跨越的模块边界、相同业务规则的重复实现。

自定义 Hook 仍运行原底层 Hook。上一轮 page-state 拆分改善了职责归属，但并没有消除全部底层状态，不能据此宣布运行成本下降。模块化是进一步收敛状态的准备，不等于完成。

## 1. 首选：收敛聊天分屏的状态更新入口

证据：page.jsx 的 sideAgentSplitByChat、artifactSplitByChat、changeSplitByChat、resourceSplitByChat 分别保存内容；split-selection-controller.jsx 的快照和恢复要逐个读取、写回四种状态。浮动面板还有独立恢复快照。

建议先限定在既有 detail split，建立每会话的 SplitSelection 数据与 open/close/restore 转换。页面和各资源控制器调用语义操作，不传四组原始 setter。先完整保留四种历史槽位与既有展示优先级；只有证明槽位确实互斥且不用于关闭后的恢复，才能改成单一 kind/payload。

不要合并 activeSideAgentByChat 和 sideAgentSplitByChat：源码明确要求列表选中不自动打开分屏。也不要合并 paneColumnWidth 与 sideAgentSplitWidth：两者有独立宽度约束与视觉用途。通用卡片布局、项目工作区、浏览器展示模式也不能因为名字相似而删除。

收益判据：快照与恢复只有一套实现；外部不再直接写四类分屏状态；未修改会话保持对象引用；不新增整页 effect 或全表扫描。

验证：打开 A 后浮动打开 B、关闭 B 恢复 A；会话切换后分别恢复；删除资源清理；项目面板不被刷新选中聊天；独立窗格归还；浏览器内容只挂载一次。先对旧行为建立同输入、同操作序列的对照测试。

## 2. 输入框：统一会话切换的设置解析

证据：composer.jsx 的 chatId effect 在保存旧附件后加载新附件，还设置权限、Soul、工作区、两种记忆、推理强度、上下文激活及菜单状态。其他 effect 同时根据插件和 contextOptions 更新其中部分值。

第一步提取无副作用的设置解析函数，明确保存值、默认值、插件可用性如何共同决定初始结果。区分“用户选择”“当前是否可用”“实际发送值”，保留用户显式 false 与字段缺失的区别。按当前语义保留需要立即清空的选项，不擅自增加跨禁用恢复。

第二步只把确实同步变化的一组设置交给局部状态转换，避免每次新增选项都要修改多处重置逻辑。草稿、附件的保存顺序与 ref 同步仍需明确的副作用边界，不能把存储写入 reducer。主聊天与快捷聊天命名空间继续隔离。

收益判据：一条默认规则只有一个权威解析位置；切换设置以一个完整结果更新；外部调用者不需要知道设置内部字段。仅用对象包住 14 个 setter，不算达成。

验证：有/无历史设置、显式禁用、插件关闭、外部 Agent、项目切换、快捷聊天、发送失败恢复、IME、附件及流式指导。性能检查聚焦输入响应与渲染提交，不以 Hook 减少代替测量。

## 3. 发送后端：显式阶段数据，降低字段的时序耦合

证据：_SendOperation.execute 串行调用 parse、load_chat、load_project/model、prepare、persist、plugin workflow、finalize、dispatch。大量字段在这些阶段内才出现，后续方法默认前置阶段成功执行。workflow 失败还有已有的持久化回滚错误处理。

建议先将请求解析结果建成明确的不可变记录，再让模型/上下文准备返回另一份准备结果；运行中的提交状态与回滚记录由独立操作对象保管。保留现有执行顺序、错误码、用户可见错误和回滚时机，不新增异步任务或通用流水线框架。不能只把所有 self 字段放入一个可变 context 字典。

先做解析与准备，不在第一轮重写 commit/rollback。Answer 与 wake 流程只有经过正常、等待用户、取消、失败结果合同逐项对照后，才考虑复用已有 finalization 服务。

收益判据：输入数据不再依赖散布的 self 写入；阶段所需字段可从签名看出；同一提交和回滚仍只有一个所有者。

验证：请求幂等、重试/分支、插件启动失败回滚、权限、外部 Agent、断开连接、错误响应、流式顺序与首次输出延迟。

## 4. 协议流：按现有协议建立解码器

证据：handle_stream 同时处理 Anthropic、OpenAI Responses、Gemini 和 OpenAI chat 类协议，分支内分别更新文本、思考、工具调用、usage、结束原因及诊断状态。

保留共同 HTTP/SSE 传输、时序统计和终止检查；把各协议状态累积放到明确的解码器。选择协议应发生在流开始时。按需输出事件，避免为每个 token 引入深复制、排队、额外 task 或全量历史规范化。

不能把供应商差异压成丢字段的最小公共格式。保留工具参数分片、索引/ID 对应关系、reasoning、usage、incomplete/failed、损坏 JSON 诊断及回调 await 的背压。

验收以录制/构造的协议事件逐条回放，对比回调事件序列和最终结果；再测首事件延迟、事件吞吐和分配成本。这部分收益明确，但属于高风险热路径，安排在状态与请求数据收敛之后。

## 5. Rail / Topbar：收敛列表投影与交互职责

Rail 已有 rail-model、rail-ordering、rail-drop-controller，不应再建立平行的排序框架。下一步逐项核对过滤、置顶、分组、可见区和拖动是否反复解释同一数据，复用确定相同的计算。展示组件只接收所需行数据和语义操作。

不要直接把三个筛选列表合成一次计算并缓存：必须先区分查询、项目、运行状态、拖动临时顺序等失效条件。也不要给每个小卡片增加各自的网络订阅。避免组件拆分时改变 key，造成滚动位置、焦点或输入丢失。

Topbar 同理，先建立资源展示合同，确认各种资源的固定、排序、拖动与激活差异，保留差异后再复用。当前阅读只能确定集中度高，不能宣称所有相似分支都是重复。

## 6. Electron / AgentSession：只按完整资源生命周期拆

BrowserTabManager 构造中能识别选择器窗口、模糊事件处理器、隐藏 timer、聊天覆盖层、全屏窗口和恢复处理器等组。第一刀宜限定选择器的创建、更新、隐藏、计时和释放；随后才考虑全屏所有者。对象接收具体依赖，不拿整个 manager 回头修改全部字段。保留 persistent partition 的共享登录、tab/session 隔离及关闭语义。

AgentSession 先检查已有插件、权限、transition 提取后的接口是否仍回写大量宿主字段，再考虑事件发布与恢复结果的数据合同。不能再提出“提取一个已提取的 driver”作为新收益。锁、取消与提交竞争、恢复不重复执行必须沿用既有边界和测试。两项都需要额外集成/跨平台验证，优先级低于前面的局部改动。

## 7. 让复杂度检查识别耦合，而不是奖励搬家

现有检查已涵盖函数长度、决策、嵌套、直接 Hook、方法/字段、setter 目标、订阅、语法恢复错误；CI 已运行预算检查。建议增量改进：

1. 追加领域聚合报告：page + 分屏控制器、composer + 子 Hook、发送 + 阶段模块作为固定责任组。用互不重叠的函数自身指标汇总，避免把外层行数和内部函数行数重复相加。共享模块归属固定，不为了过预算临时排除。
2. 增加状态写入面报告：统计关键 ref/字段/setter 的写入函数与模块。当前 setter_targets 依赖命名正则，不识别全部别名、多层属性或通用 setter；直接 ref.current 写入也未被覆盖。先补基于语法和绑定的识别与测试，动态无法解析处标明未知，不宣称精确完整。
3. 资源检查从报告开始：列出 timer、事件、请求、observer 与 dispose/cleanup。单纯统计 addEventListener 数无法证明泄漏，不能未经控制流分析就将“没有同名 remove”作为硬失败。
4. 细化领域依赖：当前 private import 检查以前两个模块段划包，不能看到 Workbench 内领域、插件之间所有私有边；顶层 import 环检查不等于运行期无环。新增边分成公开合同和内部实现，再设增量护栏。
5. 基线变更记录新增、收紧、移动、删除及理由。匿名编号移动继续验证源码一致，不能通过整体重新生成放宽预算。
6. 指标之外保留行为与性能门槛：接口/事件序列对照、关键状态转换、请求数量、重复投影次数、渲染提交和资源回收。性能对比固定数据与环境，记录提交和依赖；先确认基准实际执行了改动路径，再解释 p95。

领域聚合复杂度不应强制每次重构下降：分离职责可能保留所有必要分支。聚合报告的用途是防止误称删除复杂度；是否成功仍看写入口和维护成本是否实质下降。

## 推荐实施顺序

1. 分屏选择的单一更新入口；同步补状态写入面报告。
2. Composer 会话设置解析与转换，保留草稿/附件副作用顺序。
3. Send 请求解析与准备数据合同；提交回滚作为单独后续切片。
4. Rail 投影与交互归属；Topbar 在确认实际共性后推进。
5. 协议流解码器、Electron 选择器生命周期、AgentSession 的剩余耦合分别立项验证。

每次完成全部修改和自审，再运行一次与改动范围匹配的验证；失败才复测受影响部分。源码字符串断言若只锁死文件位置可以迁移/替换，先保留等价行为覆盖；测试长或运行慢本身不是删除理由。

不要以删协议、删平台、删兼容处理、降低刷新频率、延后首 token、吞异常或取消交互来达标。不建议为本目标做全量类型迁移、换框架、微服务化或引入万能状态容器。
