# Cyrene Doctor 通用修复能力研究

日期：2026-09-08。状态：设计研究；首条插件补丁链路已实现，范围见下方实施记录。基于当前工作区代码和文末一手资料；未读取用户真实对话、凭据或运行数据库。

## 实施记录

已实现独立修复 Agent、插件/契约读取、冻结复现、最多三份候选补丁、静态及 macOS 隔离验证、完整 diff 预览、方案哈希提交、并发版本保护、持久原文件与步骤记录、失败补偿、取消与重开恢复，以及 WebUI/API 入口。第三方插件不需要发行版备份；普通固定修复计划也改为独立保留。

当前仅生成一个选定插件内已有 Python 文件的补丁。动态执行在非打包 macOS 上可用，其他运行环境明确降级为静态验证；macOS 内存用量由宿主轮询并终止超限进程，属于监测阈值而非瞬时硬内存隔离。类型化配置组合、精确 Hook 恢复、离线提交、其他平台执行器和发行版内核更新仍是后续阶段，不能将本次交付视为下文所有设计均已实现。使用说明见 [Doctor 文档](../docs/doctor.zh-CN.md)。

聚焦验证共覆盖 64 项 Python 用例（包括新加的 18 项生成修复用例）和 9 项前端用例，均已通过；前端构建通过。使用可控模型响应验证 Agent 工具闭环，并实际执行 macOS 沙箱用例验证修前失败/修后通过及宿主文件、只读源码、网络访问限制，未使用真实模型额度或更改用户安装插件。

## 1. 建议决策

将 Doctor 扩展为一个专用修复 Agent：可以主动取证、提出假设、在隔离副本中修改任意受支持的插件代码、运行验证，再通过宿主将具体变更提交到真实环境。复用 AgentSession、模型网关和既有领域服务，不另造 Agent 内核。

“通用”的判断标准是：面对未事先编写故障规则的问题，能够根据证据生成新补丁或组合操作，并验证原问题；不是为每个错误码增加一个按钮，也不是承诺修复所有故障。执行能力可以是有限的通用原语，修复内容由 Agent 根据问题生成。

建议首个完整版本覆盖：可编辑插件实现、工具覆盖、可验证的配置问题，以及通过既有领域接口恢复的失败任务。应用内核缺陷在源码开发环境生成补丁；发行安装环境走修复版本/更新包，不能假定用户安装目录是可编辑 Git 仓库。

用户点击“修复此问题”后，范围内的取证、构造副本、编辑和测试连续执行。提交真实环境的授权绑定具体资源、变更及验证方案；已有授权覆盖时直接继续，仅在扩大范围或需要用户选择时暂停。研究本身不需要启动修复或改变现有权限设置。

## 2. 当前实现可复用什么、缺什么

| 代码入口 | 已有能力 | 扩展要求 |
| --- | --- | --- |
| `platform/doctor/agent_analysis.py:analyze` | 独立 AgentSession、模型桥接、证据引用、取消 | 目前只读报告，新增修复会话及动态取证工具；保留轻量分析模式 |
| `core/session.py:AgentSession` | 工具循环、ContextTree、权限请求、事件 | 复用内核；Doctor 自有能力边界必须先于宽松的全局权限生效 |

| `plugins/plugin_restore.py` | 内置插件恢复及文件指纹 | 继续支持整体恢复；新增保留自定义的精确补丁，不要求目标有内置版本 |
| `platform/settings_service.py`、`builtin/cyrene_application/settings_update.py` | 类型化配置、revision、授权和幂等操作示例 | 宿主适配器复用服务层，避免依赖待修插件的工具实现或复制其业务逻辑 |
| `observability/debug_event_repository.py` | 事件摘要及详细事件读取 | 增加按 incident/run、时间范围和字段白名单过滤；原始事件不能直接全量交给模型 |
| `platform/doctor/repository.py:record_incident` | run ID、阶段、分类、栈位置 | Doctor scope 目前未接受 run_id；建立 run → 工具调用 → Hook/job 的可查询关联 |
| `core/context/hook_store.py:retry_failed` | 批量失败投递恢复 | 增加精确 delivery 恢复，并校验执行者、业务提交和副作用，不调用批量重放解决单项问题 |
| `platform/run_coordinator.py:maintenance` | 进程内空闲期维护保护 | 可继续用于在线提交；离线与在线交叉访问需另外实现跨进程互斥 |
| `core/plugin/core_impl/bash.py` | 超时、取消、子进程组清理 | 当前是宿主 shell；工作目录和权限审核不是 OS 沙箱，不能直接作为试修执行器 |

额外基础问题：现有检查会给非内置插件生成无法执行的恢复动作；前端吞掉方案请求的具体错误；修复结果和普通报告共用按最近 200 个 JSON 清理的仓库。这些应随新流程解决，避免不可用动作、错误不透明和恢复记录被普通报告挤掉。

## 3. 方案比较

| 方案 | 是否获得通用能力 | 成本与局限 | 建议 |
| --- | --- | --- | --- |
| 增加固定 repair action | 只能覆盖预设问题 | 交付快，未知代码缺陷仍无法处理 | 保留为快速路径 |
| 将普通聊天 Agent 的全部工具接给 Doctor | 能尝试任意修改 | 同宿主执行、受坏插件影响、缺少事务及原故障验证 | 不作为默认架构 |
| 专用 Agent + 隔离执行器 + 宿主提交器 | 能生成新补丁、组合已有领域操作 | 需补齐执行隔离、产物契约和验证 | 推荐 |
| 外部编码 Agent 作为执行器 | 可生成代码补丁 | 引入安装、账号、权限、数据流和版本依赖；仍需统一提交与验证 | 可选适配器，后续再做 |

核心不是换模型或放大 prompt。通用能力来自调查、编辑、执行反馈的循环；可靠性来自执行器和验证契约。

## 4. 一次修复的闭环

```mermaid
flowchart LR
  A[问题与故障记录] --> B[主动取证与假设]
  B --> C[生成最小复现和修复副本]
  C --> D[修改与隔离验证]
  D -->|失败且仍有预算| B
  D -->|通过| E[冻结具体方案与授权范围]
  E --> F[宿主校验并提交]
  F --> G[原故障验证]
  G -->|解决| H[已验证修复]
  G -->|失败| I[回滚或记录部分完成]
```

示例：第三方插件因返回类型不符合协议而报错。Agent 读取目标插件和对应协议，使用故障参数的最小替代样本复现，修改副本中的返回值适配，运行契约测试，展示精确 diff；宿主检查插件指纹、备份、应用和重载，再执行同一契约探针。无需预先存在该错误的专用 repair action，也无需将整个插件恢复成发行版。

失败聊天的原轮次不会默认重放。若已发生发信、支付、文件写入等副作用，应以独立探针、模拟结果或领域恢复接口验证；无法安全重现时明确显示“变更已应用，原问题尚未验证”。

## 5. Agent 工具与执行边界

建议以下为工具契约方向，名称均为待新增 API。

| 工具类别 | 示例能力 | 实际执行边界 |
| --- | --- | --- |
| 证据 | `query_incident`、`inspect_run`、`read_scoped_events` | 宿主按授权 ID、时间和大小返回投影，附来源、版本和缺失说明 |
| 环境 | `inspect_capabilities`、`read_effective_settings`、`inspect_plugin` | 展示有效配置及来源，凭据仅返回存在性/引用；失败模块不能成为唯一证据入口 |
| 文件 | `read_artifact`、`search_artifacts`、`apply_patch` | 只对 manifest 中的副本资源操作；解析后的路径、符号链接和文件大小由工具强制检查 |
| 执行 | `run_in_sandbox`、`run_probe` | 有真正隔离时允许运行生成脚本；无隔离时仅允许宿主实现的静态检查 |
| 计划 | `submit_repair_plan` | 提交 diff、领域操作、前置条件、验证目标和副作用说明；宿主重新计算而不信任模型声明的范围 |
| 提交 | `apply_approved_plan` | 模型只提交计划 ID；宿主核验授权和哈希，禁止通过参数夹带临时新命令 |
| 验证 | `verify_repair` | 执行冻结的验证方案，返回真实结果；模型不能直接将状态设为已修复 |

Doctor 的工具实现应随可信宿主发布，不从损坏的 `plugin_impl/` 加载 Read/Edit/执行器。AgentSession 使用独立 registry 和最小服务集合；不继承普通会话 SOUL、自动 Skills、MCP 和启动 Hook。需要读取某个 Skill 排查问题时，将其作为证据文件，而不是自动执行指令。

现有 `permission_user_request` 和权限事件可以承载明确用户意图与 UI 交互，但 shell 的 OS 约束、计划有效性和权限范围必须由确定性代码检查。不能把 `read_only=False`、全局 full_access 或 LLM 权限审核结果当作完整修复授权。

## 6. 隔离副本的真实要求

推荐抽象 `RepairExecutor`，最少报告 `static_only` 或 `isolated_execution` 能力。首版先交付确定可用的一个平台实现，其他平台清楚降级；不要为跨平台表面一致而回退到宿主任意执行。

- 仅挂载目标源码副本、必要只读依赖与测试样本；可写范围限本次 scratch、输出和临时数据库。Git worktree 便于生成补丁，但本身不是沙箱。
- 不继承宿主环境变量、真实 HOME、密钥、Docker socket 或生产数据库路径。当前 `external_process_environment()` 主要处理打包库路径，不是密钥清理器。
- 执行生成代码需要同时限制文件、网络、子进程、CPU/内存、时间及输出大小。Python import、pytest fixture 和安装脚本均会执行代码，不能按“测试命令”视为只读。
- 本地诊断默认关闭网络及到真实 localhost 服务的访问。模型请求由隔离区外的网关代理承接；需要 provider 探针时由宿主通过受限请求调用，密钥不进入修复副本。
- SQLite 副本使用一致性备份机制或停止写入后的完整快照，不能运行中只复制主数据库文件而漏掉 WAL。副本做范围缩减及脱敏，并记录脱敏是否影响复现。
- 目标系统相关错误必须用对应 OS 的执行环境验证。Linux 容器通过不代表 macOS/Windows 宿主兼容。

候选后端：本机 OS 隔离可减少桌面运行开销；容器适合可重复的 Python/插件契约验证，但有运行时安装成本。本文不锁定具体跨平台沙箱库，选型需再用目标安装包验证平台支持、子进程封锁与发布许可。

## 7. 提交和恢复不能只是“调用工具成功”

建议新增持久 `RepairSession`、不可变 `RepairPlan`、执行账本 `RepairJournal`。普通诊断报告保留现有轻量仓库，修复计划、备份及未结束会话独立保留，完成前不进入按数量清理。

计划最少包括：`incident_refs`、授权范围、目标版本/指纹、具体文件 diff、类型化配置变更、顺序化领域操作、前后置条件、验证定义、备份引用、不可逆副作用、预算和计划哈希。资源路径由宿主 ID 映射，不能直接信任模型提交的绝对路径。

提交流程：

1. 校验当前安装版本、配置 revision、文件指纹和授权仍匹配；变化则重新规划，禁止覆盖并发编辑。
2. 获取真实资源的维护锁。副本研究期间不长时间占住应用维护锁；提交时才进入安全边界。在线和离线共享进程锁/文件锁契约，不能只依赖现有 RLock。
3. 备份后先持久记录该步骤意图，再执行原子文件替换或领域更新，随后持久记录结果。多文件/多服务操作不是一个天然原子事务，应为每步定义补偿操作。
4. 重载并验证。热重载影响范围必须依据真实 loader 能力；目前 `reload_user_plugins(seed=False)` 不能据此宣称仅重载目标插件。
5. 验证失败时，对指纹仍一致且可逆的步骤进行补偿；如果已有外部副作用或新并发修改，显示部分完成和剩余处理事项，不能强制回滚。

步骤幂等键在真实服务端校验。进程恢复遇到“已写意图但未写结果”时，先读取实际状态判断是否已经执行，不能盲目重放。取消发生在提交期间，应完成当前不可分步骤并记录状态；重启应用的任务由外部恢复入口接管下一阶段。

UI 状态至少区分：调查中、构造方案、验证中、待提交、提交中、已验证修复、已应用但未验证、未解决、需要信息、已回滚、部分完成。现有 `applied` 只表示动作执行，不能自动升级为“故障已解决”。历史 incident 保留为历史事实，用 resolution 关联新验证，避免复检时永久把旧事件计作当前故障。

## 8. 验证如何防止“看上去修好了”

修复前冻结成功条件：例如“该插件能加载且同一协议样本返回有效结果”，而不是笼统“doctor 没有失败项”。生成补丁和最终判定必须隔离职责，但不要求运行两个模型 Agent：首版由一个 Agent 工作、宿主验证器判定即可。

- 代码类：最小复现修前失败、修后通过，同时通过受影响契约检查。复现不了时只报告推测或未验证补丁。
- 配置类：校验字段与生效范围后，验证确实采用了预期配置，而不是只看持久化成功。
- 模型类：最小请求能验证连通性，不能证明长流式响应恢复；按故障类型提供对应无副作用探针。
- 记忆/Hook：检查目标任务及提交记录；冻结快照的正常行为不作为故障，也不清除状态绕过校验。
- 行为类：用户认为回答质量异常时，以经用户认可的样例和对比为依据；没有客观标准时保留主观验收，避免宣称自动证明修复。

Agent 可以补充测试，但不能删除既有测试、降低协议要求或修改宿主验证状态获得通过。最终判定只读取独立验证输出；同一个 Agent 修改代码和测试后自述成功，不足以成立。

建议初始预算作为可配置产品默认值：每次最多 3 个候选补丁、15 分钟、30 次模型调用，并设置总 token/金额上限（金额估算不可用时按 token 和调用数限制）。这不是性能测量结果；应以故障集评测再调整。模型请求恢复和修复尝试分别计数，恢复策略不能自动重发有副作用的操作。

## 9. 离线、自身故障及发行环境

基础离线检查继续在加载用户插件之前启动。新增离线恢复 runner 是独立模式，不必把现有 `--offline` 默认行为改成写操作；执行已批准计划可使用同一计划/账本协议和跨进程锁。

主服务坏了但轻量 Python 仍可用时：runner 读取最小配置投影，使用可用模型通道或只执行已有确定性计划；不启动整个 PluginApplicationHost。主模型不可用时，只有事先配置且被授权的备用模型可使用，不能指望坏掉的模型修复自身认证。

Python/打包运行时本身损坏时：Electron 恢复入口提供可验证的更新或安装恢复；如未来需要这种情况下仍能 AI 生成修复，必须另附可独立运行的受信 runner 或明确配置远程服务，这是一项额外发布工程。

发行版内核、Doctor 自身执行器和权限模块不作为在线自修改目标。插件源码可以生成补丁；打包内核缺陷产出版本化修复材料，走正常构建和更新。数据库缺失的历史证据、密钥丢失、第三方服务故障需要恢复源或外部处理，均有明确“无法自动完成”状态。

## 10. 实施顺序和验收

**阶段一：把现有修复变成可信基础。** 增加动作可用性与原因；结构化错误展示；独立计划/账本保留；`applied` 与 verification 分离；修复原有三个动作的恢复与状态一致性。阶段完成仍不应宣传通用修复。

**阶段二：交付第一条通用代码修复闭环。** 新增主动读取目标代码/事件的修复 Agent、一个真实隔离执行后端、生成 patch、最小复现、宿主提交与回滚。以“没有发行版备份的自定义插件出现未知契约错误”作为主验收场景。与阶段一合起来是首个有价值的交付范围。

**阶段三：扩大领域。** 接入类型化配置变更、模型探针、精确任务恢复、跨文件补丁，以及会话重启后的恢复；每个领域声明前提和验证方式。

**阶段四：拓展运行条件。** 离线提交、独立 runner、其他平台隔离与安装包测试；外部编码 Agent 仅作为统一协议下的可选执行器。

建议代码划分（均为新增设计）：

```text
platform/doctor/
  agent_repair.py        修复 AgentSession 组装及有界循环
  evidence_sources.py   范围化取证及脱敏
  repair_contracts.py   会话、计划、步骤、验证结果
  repair_workspace.py   一致性副本和资源 manifest
  repair_executor.py    静态/隔离执行器接口
  repair_commit.py      授权、锁、备份、领域适配和补偿
  repair_journal.py     持久步骤、幂等和崩溃恢复
  repair_verification.py 原故障和回归检查
```

另扩展 `workbench/http/system/doctor.py` 与 `frontend/features/doctor/doctor.jsx` 提供修复会话、进度、具体 diff 和验证结果；既有报告和固定恢复接口保持兼容。领域适配器复用平台/插件服务，避免把所有业务逻辑堆进 Doctor。

验收集至少包括：第三方插件语法错误、未知返回契约错误、多文件依赖问题、配置覆盖冲突、输出截断、记忆任务冲突、Hook 部分提交、模型不可用、补丁期间用户编辑、提交时强杀、沙箱路径/网络越界、故障无法复现。用故障注入覆盖机制，用未参与开发的未知缺陷评估生成能力。

分别报告：原故障实际解决率、错误宣称成功率、引入回归率、恢复成功率、用户介入次数及成本。确定性发布门槛为：越界提交、重复外部副作用、覆盖并发修改和虚假“已验证”在验收集中为零；通用解决率不能仅凭单个演示推定。

实现完成并自查后集中运行聚焦测试（Python 用 `uv run pytest ...`），再做受影响平台的安装包端到端验证。本研究仅新增文档，不运行产品测试；前一轮已有 36 项 Doctor 测试通过，不视为新设计的验证。

## 11. 外部研究依据与适用限度

- [SWE-agent Architecture](https://swe-agent.com/1.0/background/architecture/)：Agent 与执行环境分离，工具经环境运行，SWE-ReX 部署容器。支持本方案的执行器抽象；代码修复架构不能直接代替 Cyrene 的运行数据提交协议。
- [SWE-agent Tool configuration](https://swe-agent.com/1.0/reference/tools_config/)：工具集合、环境变量传递、单次与累计执行超时具有独立配置。支持明确预算和环境契约，而非给 Doctor 无界 shell。
- [Anthropic: Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)：讨论跨会话进度产物、增量工作及缺少端到端验证导致过早宣告完成。这里借鉴持久进度和验证闭环，不照搬其多 Agent 结构。
- [Anthropic: Beyond permission prompts](https://www.anthropic.com/engineering/claude-code-sandboxing)：讨论 OS 级文件和网络隔离，让 Agent 在既定范围内更自主地执行。它是设计参考，不是对任意沙箱库、Windows 支持或 Cyrene 当前安全性的保证。
