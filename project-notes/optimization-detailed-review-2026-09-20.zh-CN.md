## 1. [P2] 临时日志读取失败被永久缓存成空结果

位置：`src/cyrene/observability/debug_event_repository.py:95–105`。

`_read_jsonl()` 会吞掉 OSError 并结束迭代；新增缓存层把这种失败与“成功读取了一个空文件”当成同一情况。只要两次 stat 相同，就将空/部分摘要作为有效缓存安装。

可复现步骤：

1. 创建包含一条已有事件的 `debug_archived.jsonl`。
2. 第一次打开文件时注入临时 `OSError(EMFILE)`，模拟文件描述符暂时不足。
3. 移除故障，文件本身的 inode、长度、mtime、ctime 不变。
4. 原版下一次查询恢复返回该事件；优化版仍返回空事件列表。

这不是只影响失败当次请求：对不再写入的归档文件，遗漏会一直持续，直到缓存淘汰或进程重启等事件发生。读取中途的临时错误同样可能缓存不完整结果。

建议：让读取层显式返回“是否成功读到 EOF”的状态，只有完整成功才允许缓存；失败结果可以沿用原来当次跳过/部分返回的语义，但不能作为有效缓存。补充首次 open 失败和读取中途失败后恢复的回归测试。

证据：`read_failure_repro.py`、`read-failure-reproduction.json`。复现只注入文件打开故障，不修改产品函数实现。

## 2. [P2] 缓存大小计量能把正常的限量查询变成 HTTP 500

位置：`src/cyrene/observability/debug_event_repository.py:99`。

`json.dumps(..., ensure_ascii=False).encode("utf-8")` 对所有文件摘要重新编码，位于最终排序/limit 之前，且没有异常保护。JSONL 中的转义孤立代理字符（例如 `"\ud800"`）可被 `json.loads` 读取，但不能按严格 UTF-8 直接编码。

复现使用两条事件：旧事件的 model 字段含该字符，新事件完全正常。请求 `/api/context-debug/events?limit=1` 本应只返回正常的新事件。

| 版本 | 实际 HTTP 结果 |
|---|---|
| 改动前 repository + route | 200，返回新事件 |
| 当前 repository + route | 500，Internal Server Error |

因此，即使异常旧事件并不属于返回内容，新增缓存的计量过程也会破坏原来成功的查询。这里验证的是本地合成日志的容错边界，不代表所有正常模型服务都会生成此类字符。

建议：采用不会改变读取结果的安全计量方式，或者在无法计量时放弃缓存并返回原结果。不能简单吞掉整次查询或删掉更多历史记录。加入“异常记录位于 limit 之外”的 HTTP 回归。

证据：`http_repro.py`、`http-reproduction.json`，使用 FastAPI TestClient 验证真实路由返回码；`reproduce.py` 也验证了 repository 层异常。

## 3. [P2] 正常模型元数据让历史消息渲染优化完全失效

位置：`src/cyrene/workbench/webui/frontend/features/chat/message-memo.mjs:12–14,26–27`。

快照只接受标量字段，遇到任意嵌套对象就返回 null。与此同时，生产回复的 `ChatReplyFinalizationService._assistant_message()` 在 249–251 行调用 `runtime_model_message_fields()`，正常 token 用量和模型身份会生成 `usage`、`latestRequestUsage`、`modelIdentity` 对象。只要其中任意一个存在，消息就永远不能被 memo 跳过。

这不是只有复杂卡片才出现的例外。普通纯文本模型回答也通常带 usage 数据，不应把“带模型元数据的纯文本消息”等同于附件/复杂卡片。

本次从实际 `runtime_model_message_fields()` 生成元数据，加入历史消息，重新运行同样的生产 React 组件夹具。每场景 3 次挂载、每次 5 次增量更新；独立计数轮次结果如下：

| 场景 | 原版每次消息主体渲染次数 | 当前每次消息主体渲染次数 |
|---|---:|---:|
| 1,000 条带元数据历史 + 1 条更新消息 | 1,001 | 1,001 |
| 2,000 条带元数据历史 + 1 条更新消息 | 2,001 | 2,001 |
| 1,000 条带元数据历史 + 1,000 条无元数据实时记录 | 2,000 | 1,001 |

另一个去掉计数插桩的轮次中，1,000 条历史 + 1 条更新的增量提交/同步布局为 8.6 → 10.1 ms；2,000 条历史 + 1 条更新为 16.2 → 19.3 ms。这些是本机合成场景的中位数，不代表所有真实会话的固定退步比例；计数结果则直接确认了快路径未命中。

全部消息和流式片段完整性检查通过。问题是优化未命中，而且新增包装层/检查仍有成本。原先“2,000 → 1”的计数来自没有任何 usage/modelIdentity 的简化夹具（原 `browser.jsx:12–13`）；不能据此说明典型历史会话的重复渲染已解决。

建议：采用能保留可变字段检测、又覆盖生产 DTO 的比较/快照策略，例如对实际使用的嵌套元数据建立受控快照；保持附件、复杂卡片的安全边界。不要通过删除 usage/modelIdentity 来换取命中率，那会改变功能。应以生产序列化输出构造性能夹具，并加入这些字段变化时界面仍刷新的测试。

证据：`production-message-fields.json`、`component-*-counts.json`、`render-review-summary.json`；另外保存了无计数插桩的重复测试结果，不能把插桩耗时当正式基准。

## 4. [P2] ASCII 快路径使中文和密集 ANSI 输出明显退步

位置：`src/cyrene/plugins/builtin/cyrene_code/terminal/history.py:60–76`。

原来逐字节循环现在额外执行 Python while 控制、状态判断；即使字节不是可打印 ASCII，仍可能执行 decoder.getstate() 和必然失败的正则匹配。中文 UTF-8、ESC/换行密集输出无法获得长 ASCII 段的收益，却承担这些新成本。

同进程加载原版和当前模块，512 KiB 数据、4 KiB 分块，交替执行顺序，1 次预热后各 5 个样本：

| 负载 | 原版中位数 | 当前中位数 | 变化 |
|---|---:|---:|---:|
| ASCII 行 | 125.88 ms | 21.61 ms | 更快 |
| 中文行 | 133.23 ms | 173.16 ms | **慢约 30%** |
| ANSI 颜色控制 + 单字符行 | 54.75 ms | 79.50 ms | **慢约 45%** |
| 中英文与 emoji 混合行 | 133.58 ms | 91.22 ms | 更快 |

每组均比较全部输出行和解析器最终状态，结果相同。这是性能回归，不是文字丢失；局部解析时间不能直接换算成整个 Agent 或终端的同等退步。

建议：在进入昂贵检查前先按当前字节筛选，避免非 ASCII 字节做无效匹配，并评估如何让无收益输入沿用低开销循环。回归矩阵应包含长 ASCII、中文、混合文本、短 ASCII 段与密集控制码，而不能只用长可打印文本证明整个终端变快。

证据：`reproduce.py`、`reproduction.json`，有全部原始采样，结果不是 cProfile 插桩耗时。

## 测试结果与验收建议

本次再次执行差分，6,000 个时间线事件、6,923 次终端分块/恢复检查、300 组任务投影仍一致。

本次相关既有 Python 测试 **56/56 通过**，但上述两项功能回归仍可稳定复现。这说明“现有测试通过”不足以支持零影响验收，需要补充针对这些边界的测试。

前一次全量 Python、前端 182 项和 33 组 UI/47 份动画结果仍然是其覆盖场景的有效证据。本次没有修改这些旧结果，也不把它们当成已经覆盖异常日志和生产元数据性能的证据。

建议先修复两项日志功能回归，再解决生产历史消息的缓存命中及终端非 ASCII 退步，然后针对最终实现重跑相关差分、浏览器和负载矩阵。共享工作区其他功能的测试失败仍应单独处理。
