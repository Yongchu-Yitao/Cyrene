# Cyrene 移动端体验研究与实施决策

2026-09-09。基于当前 Android 壳、Workbench 前端源码、此前真实聊天验证及官方文档。
本轮模拟器已离线，因此没有新的设备性能或交互测试；下述指标是建议验收目标，不是测量结果。
延续 UI/UX Pro Max 的触控、可访问性和响应式原则，保留 Cyrene 现有视觉语言。

## 1. 产品定位与优先顺序

建议定位为“随时交办任务、查看进度、处理待确认事项、带走结果的随身工作台”。
完整能力保持可达，但手机的默认视图优先服务短时、单手、经常被打断的使用场景。
终端、复杂看板与多文件操作仍有入口，平板及外接键盘恢复更高信息密度。

优先级：恢复可靠性 → 输入与阅读 → 任务反馈 → 文件流转 → 导航和复杂页面 → 视觉精修。
UI 可用性与运行时稳定性分别验收。先前 TCG 启动耗时达分钟级，组合工具触发 SIGILL；
这些问题不能用动画、进度条或常驻后台承诺掩盖。

## 2. 本次新增的源码发现

| 证据 | 体验影响 | 决策 |
|---|---|---|
| WorkbenchProxy.kt 使用 ServerSocket(0)，origin 含动态端口 | 重建代理可能进入新的浏览器存储分区 | 持久化身份不能依赖临时网络地址 |
| messages.jsx 的草稿、附件元数据、工作目录覆盖写 localStorage | 同页刷新恢复不等于应用重启恢复 | 为草稿、附件和活动位置建立独立持久化接口 |
| composer-draft.jsx 已监听 pagehide/visibilitychange | 常规切后台已有保存机制；强杀未必触发事件 | 保留现有防抖，增加持久化确认与异常退出恢复 |
| pane-workspace-persistence.mjs 仅保存包含终端的特定布局 | 不能当作所有资源和页面的通用恢复方案 | 明确定义移动端活动面板、返回栈、阅读锚点 |
| DesktopWorkbenchActivity 无自定义返回协调、saveState/restoreState | 页面内返回与系统返回尚未形成统一链路 | 接入系统返回并维护 Web 路由栈 |
| WorkbenchModel.start 在启动成功后直接设 ready | ready 不能完整代表页面、模型、任务健康状态 | 分开运行时、连接和任务状态 |
| 文件选择统一 OpenMultipleDocuments，下载仅支持本机 HTTP URL | 相册、拍照、分享进入及 blob 导出链路不完整 | 原生桥优先用于系统集成 |

localStorage 按 origin 隔离，origin 包含协议、主机和端口。因此上述端口风险是源码与浏览器规则的推论，
本轮未在设备重启复现；它不意味着后端已保存的聊天记录丢失。[MDN](https://developer.mozilla.org/en-US/docs/Web/API/Window/localStorage)

## 3. 五条关键用户旅程

### 随时记下一项任务

打开即能看到最近工作和输入位置；运行环境尚未准备好时也能保存草稿、选择附件。
准备完成后由用户发送，避免恢复联网后自动执行旧指令。发送按钮立即反馈“正在提交”；
服务端确认后显示“已接收”，执行再展示明确阶段。请求超时先按请求标识核对状态，
不要盲目重发导致重复任务。需要后端幂等契约支持，不能只做前端按钮禁用。

### 等待任务时离开应用

显示“正在读取 3 个文件”“等待你的确认”等可核实状态，不输出虚构百分比。
关闭详细日志时仍看得到当前阶段、用时和停止入口。回前台按 run ID 恢复状态，
用事件序号补齐流式内容；若现有接口不支持游标，拉取权威快照并去重。
只有确认运行时仍存活才能说“后台继续运行”；进程退出后标记中断并提供恢复选项。
通知只用于完成、失败、待用户处理，并深链回具体任务；运行服务通知与任务通知分开。

### 收到一个文件并交给 Cyrene

从系统分享进入 → 选择项目/会话 → 附件预览 → 补充要求 → 确认发送。
图片用系统照片选择器，文档用文件选择器，拍照和麦克风权限在实际点击时申请。
附件有名称、类型、大小、进度、删除与失败重试；不要把 content URI 当作 Linux 文件路径。
导入时按需要持久化 URI 授权或复制到应用暂存目录，再上传客体；取消与失败清理临时文件。
分享接收的文本和文件仅作为草稿，不自动执行。
官方参考：[照片选择器](https://developer.android.com/training/data-storage/shared/photo-picker)、
[上下文权限请求](https://developer.android.com/training/permissions/requesting)。

### 阅读结果并核对来源

回答正文优先，工具调用折叠成阶段卡，错误与待批准事项保持展开。
代码、表格在自身区域横向滚动；每块有复制，文件有预览、保存和分享。
点开来源用全屏资源页，返回时恢复原消息与滚动锚点，不能跳回列表顶端。
流式输出只在用户接近底部时跟随；用户向上阅读时显示“有新内容”，不强制拉回。
不要逐 token 向 TalkBack 播报，按消息完成或重要阶段更新播报。

### 审查工具操作

将目标、影响、关键参数和允许/拒绝按钮集中在一个可读确认面板；重要信息无需横向滚动。
详细命令可以展开，主按钮不要与可滚动内容重叠。拒绝后说明任务状态与可继续方式。
这是已有工具审批的移动展示设计，不增加无关的确认流程。

## 4. 导航：对上一版建议的修订

不建议一开始直接把桌面五个模块改名合并成四个永久底栏。
缺乏使用频率证据时，“工作/资料”等新分类可能增加查找成本；会话页底栏还会挤占输入空间。

首版采用：会话列表首页 → 全屏会话 → 全屏资源页。首页显式列出会话、看板、日程、知识、记忆入口，
保留原功能名称。会话顶部放项目/标题、历史入口和更多，底部专注输入。
模型保留一个简短可见标签，一次点击切换；工具、上下文等进入带标签的设置面板。

将以下两种导航做原型对比：A 会话首页+模块抽屉；B 首页级“会话/任务/资料”底栏。
请使用者完成找旧会话、查日程、查看记忆三个任务，比较误入、回退、耗时，再定最终分类。
复杂工作区仍需显式“已打开资源”列表；不要靠隐藏分屏把原功能变得不可达。

## 5. 聊天输入、触控与返回

手机正文以 16px 起步，主要点击区以实际 48dp 为目标，保持系统字体缩放；
CSS px 到 dp 要实测，不能将 WCAG 的 24 CSS px 最低标准误作舒适触控尺寸。
拖拽移动看板、排序面板均提供点击菜单替代。[WCAG 2.2](https://www.w3.org/WAI/standards-guidelines/wcag/new-in-22/)

输入框从 1–2 行增长到约可用区域三分之一，之后内部滚动，支持展开编辑。
软键盘 Enter 换行，发送用按钮；外接键盘保留明确快捷键，中文组词时不得误发送。
不能仅按窄屏或 coarse pointer 判断物理键盘；发送行为应有用户设置及兼容性测试。

系统 IME 优先消费关闭键盘的返回；剩余返回关闭最上层 sheet/对话框，再返回资源来源页，
再回会话列表，最后交给系统离开。退出会话不等于停止任务，停止生成不等于停止整个运行环境。
使用 AndroidX 返回回调协调 Web 导航，禁用状态下让系统自然接管。
[Android 返回手势](https://developer.android.com/guide/navigation/custom-back/predictive-back-gesture)

由原生壳统一处理系统栏和 IME，前端根据 WebView 实际可见尺寸布局。
先测 adjustResize 与 insets，再决定 visualViewport 是否只用于诊断或补偿，避免双重缩减高度。
键盘动画使用当前目标 API 支持的兼容机制，不依赖更高版本独有行为。
[Android 键盘控制](https://developer.android.com/develop/ui/views/layout/sw-keyboard)

## 6. 架构选择

| 路线 | 收益 | 成本/限制 | 建议 |
|---|---|---|---|
| 仅添加响应式 CSS | 快速修正边距和溢出 | 无法解决返回、恢复、文件流转和分屏状态 | 只作一部分 |
| 共用 Workbench 状态与 API，增加移动布局与原生能力接口 | 保持功能一致，能覆盖手机旅程 | 需要明确桥接和状态契约 | 推荐 |
| 重写原生聊天/工作台 | 更直接控制原生交互 | 再次维护两套复杂 UI，完整功能迁移成本高 | 当前不采用 |

Android 负责系统返回、insets、分享/文件/通知、启动与错误页；Web 负责会话、任务、资源和审批。
原生桥采用有限、带版本的能力消息；校验可信主文档来源及字段，不提供任意命令执行入口。
后端认证仍只在原生代理注入，不能为了桥接暴露给 JS。

随机端口问题优先用独立持久化服务解决：草稿/活动页面按安装实例、项目、会话命名空间保存到
Android 私有存储，Web 启动先恢复、之后增量写回。避免覆写 window.localStorage 全局实现。
仅固定端口仍需处理占用和认证，不足以独立解决可靠性；稳定虚拟 origin 路线需另行验证
HTTP POST、SSE、WebSocket，不应直接用资源拦截替换现有代理并宣称兼容。
附件正文不塞进偏好存储，单独管理文件生命周期。后端历史是权威数据，本地历史缓存只是带时间标记的预览。

启动体验可分步实现：先立即显示原生启动页并允许草稿输入；下一步评估 APK 内打包同版本前端壳，
使后端未启动也能展示最近缓存。必须有前后端版本握手及升级策略，不能任意混用旧静态资源。
若 TCG 冷启动持续分钟级，应单独评估运行时改造；连接远端作为可选路径，需要用户选择，
不改变当前本机运行的产品承诺。Gemma4 服务已经在远端，更换模型位置本身不会消除本地 VM 启动耗时。

## 7. 性能与验收目标（待测）

将时间拆成启动壳、VM、Python、Web 页面、请求接收、首个模型输出，分别记录，不能只报总耗时。
建议目标：前台操作反馈 P95 ≤100ms；运行时已存活时恢复可交互页面 P95 ≤2s；
冷启动 1s 内显示可操作的启动/草稿界面。模型首输出由服务性能单独考核，不冒充 UI 性能。
这些是工程目标，尚未在当前设备验证可达。

在真实 8GB 手机测主应用、WebView renderer、Runtime/QEMU 的合计峰值内存、Swap、温度和耗电，
模拟器设置 8GB 不等于这些结果。界面隐藏时降低渲染开销，但不能据此停止后端任务或承诺省电比例。
长会话先 profile，再决定虚拟化；特别注意动态 Markdown 高度、图片加载与阅读锚点。

验收至少覆盖：360/390/412 CSS px、横屏、平板、200% 字体、明暗主题、TalkBack、中文输入法。
执行 20 次切后台/回前台，以及独立的主进程强杀、renderer 退出、Runtime 退出与端口变更恢复场景。
已确认保存的草稿和附件不得丢失；未确认提交不得自动重发；任务状态必须与后端一致。
不在用户数据上做破坏性测试，使用专用测试会话和附件。

招募 5 位代表性使用者做形成性测试（不是统计证明）：发图提问、找历史、处理确认、离开再回来、
导出结果。记录任务完成、误触、回退、帮助次数与主观负担。关键流程目标一次完成率至少 90%，
样本小时同时报告原始成功人数，不能只显示百分比。

## 8. 建议执行顺序与完成定义

P0：草稿/活动状态跨端口恢复，返回与 IME 协调，区分停止生成/停止环境，任务恢复与重复提交保护。
完成定义：重建主应用仍能恢复已保存草稿；返回不误退；键盘不遮挡；提交超时不重复执行。

P1：单栏会话与资源页、触控输入栏、真实阶段反馈、系统文件选择/分享、结果导出。
完成定义：上述五条旅程可闭环，不依赖桌面鼠标操作；真实模型、文件、后台恢复分别验收。

P2：看板列表/议程、知识与记忆列表详情、平板多栏、通知深链、可访问性与性能优化。
完成定义：桌面功能都有可发现入口，跨尺寸不丢状态，复杂模块实际可操作。

撤回上一版 8–14 日作为完整体验交付估算：新增持久化、桥接和运行时约束使该数字依据不足。
先用 P0 原型与设备验收确定接口缺口，再逐项估算。UI 工作和运行时修复分别排期。

本轮产出为研究与实施建议，未修改产品代码、未运行测试，未声称已完成新适配。
