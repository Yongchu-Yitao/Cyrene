# Android QEMU 数据库锁调查（2026-09-10）

## 范围和方法

Android 15 ARM64 专用模拟器，内层 Linux QEMU 4 vCPU / 4 GiB，使用已修复
CMLE 指令问题的 Preview APK。模型 MiniMax-M3，两轮新对话均要求只输出
1 到 80 的整数，不调用工具；本轮没有加载浏览器。模拟器时间不能代表真机。

在 guest 临时注入 SQLite 事务追踪，记录事务起止、SQL 操作类别、调用位置、
SQLite 错误码及同进程同数据库的未结束事务，不记录消息正文、SQL 参数或密钥。
第二轮额外传递 aiosqlite 的异步调用来源。诊断代码未加入产品。
追踪有开销；事务持续时间包含调度等待，不等于 SQL 执行时间。
显式读事务也会被记录，不能把所有事务都当成写锁持有者。

## 确认的冲突

第一轮复现 `ChatRunEventStore.append_many` 批量 INSERT 失败，
SQLite 错误码 5（SQLITE_BUSY），调用耗时 1.070 秒。
同一主库 `cyrene.runtime.database` 上，当时存在另一个尚未结束的 aiosqlite
事务，最终持续 3.419 秒，覆盖整个失败写入区间。主库已启用 WAL。
事件写入的 busy timeout 是 1 秒，因此 WAL 已开启并不能避免此次并发写入冲突。

第一轮异步调用来源未跨线程保留，不能确认这个 3.419 秒事务的业务函数。
第二轮补充追踪后没有再次出现 SQLITE_BUSY；不能将第二轮找到的业务直接
等同于第一轮的持锁者。

## 已定位的事务来源

| 路径 | 观察到的时长 | 说明 |
|---|---:|---|
| 第一轮 aiosqlite 事务 | 3.419 秒、2.142 秒 | 业务来源未完整记录 |
| `record_usage_stats_batch` | 0.747 秒 | 主库用量统计，第一条 INSERT 后多次 await，最后 commit |
| `mutate_chat` | 第一轮 0.984 秒；第二轮 0.577 秒 | BEGIN IMMEDIATE 后读取、复制、合并并保存会话 |
| 日程 `claim_due` | 第二轮 0.398 秒 | BEGIN IMMEDIATE 后查询、fetch、处理和提交均有异步切换 |
| `read_chat_bundle` | 第一轮 0.679 秒 | 显式读事务；不能据此认定它阻塞了 WAL 写入 |

用量统计和日程扫描会在持有写事务期间等待事件循环重新调度。
代码结构说明事件循环繁忙可能延长持锁时间，但本次没有将每段持锁时间拆成
磁盘、CPU 和调度三部分，不能给出各自占比。

Context 树数据库和媒体任务数据库位于独立文件。它们也有慢操作，但不能
作为这次主库写锁冲突的直接持锁者。聊天事件超过 6000 条才涉及的裁剪路径
在这两轮均未触发，不能把这次等待归因于大批历史事件裁剪。

## 对结果的影响

第一轮对话完成约 87.2 秒，最后游标 38；数据库保存 38 条事件，序号 1—38，
没有缺口。该次事件批次失败后补写成功，不能把错误日志等同于 Agent 失败。
第二轮完成约 81.9 秒，最后游标 125，没有观测到 SQLITE_BUSY。
这些是完整对话耗时，不能称为数据库等待时长，也不能作为两种实现的性能对照。

当前实现失败时将批次放回内存，后续 publish/最终 flush 可以重试；
它并非无限重试保证。若最终 flush 仍失败，代码会记录尚未持久化的事件数，
进程随后退出时这些内存事件可能丢失。因此需要解决竞争，不能只隐藏日志。

## 建议的修复顺序

1. 缩短用量统计与日程领取的写事务：在事务外准备参数，让同一工作线程连续
   执行事务内 SQL 和提交，避免每条 SQL 之间依赖主事件循环调度。保留统计
   原子性、异常回滚和日程租约的并发互斥，不能直接删除 BEGIN IMMEDIATE。
2. 日程没有到期任务时可以先只读检查；真正领取时仍在写事务内重新核验条件，
   避免空扫描反复占用主库写锁。须保留到期、重试及多实例领取行为。
3. 检查会话保存中可移出写事务的纯计算；依赖最新数据库内容的读取和合并不能
   为提速而直接移出，否则可能引入并发覆盖。
4. 对事件补写增加有界退避与结束阶段的可靠性验证，保留内存队列和按序号幂等
   写入；不建议通过全局提高到 30 秒或关闭持久化掩盖锁竞争。

本轮完成调查和记录，未修改产品数据库实现、等待上限或业务行为。
完整证明某项改动有效，还需要在相同 QEMU 负载下对照，并验证统计不重计、
事件游标无缺口、日程不重复领取及事务失败可回滚。

## 修复设计复核与隔离实验

后续在同一 QEMU guest 的独立 Python 进程、临时 SQLite 文件中进行两项
故障注入实验，未操作真实会话数据库，也未改产品源码。这些是机制验证，
不是正常用户请求的耗时基准，也不证明之前 3.419 秒事务的业务来源。

### 空日程扫描

初始化实际日程表，保持表为空，让另一连接持有 BEGIN IMMEDIATE 写事务。
调用现有 `ScheduleRepository.claim_due()`，5.081 秒后返回 SQLITE_BUSY。
同样锁仍未释放时，使用相同到期/租约条件进行只读 SELECT，0.021 秒返回空。

据此，第一步可以明确实现为：

1. 在后台线程建立并最终关闭连接，用自动结束的只读查询检查是否有候选任务。
2. 没有候选直接返回；关闭游标，不能携带旧读快照升级写事务。
3. 有候选才 BEGIN IMMEDIATE，并重新执行现有完整条件查询，保留排序、limit、
   lease_token、run_id 和日志写入规则；预检查结果不能作为实际领取依据。
4. 事务中的查询、领取、日志更新、commit 连续执行，异常时 rollback。
5. 不修改扫描间隔。预检查后新出现的任务由下一轮扫描发现，与轮询模型一致。

仍需验证两个进程同时领取、预检查后被暂停或删除、租约过期重领、运行标识
稳定等情形。现有测试只覆盖其中部分情况。

### 统计取消后的重复确认

使用实际 `record_usage_stats_batch` 和 `_flush_telemetry_batch`，输入一个
工具调用事件。临时包装 commit，在真实提交成功后暂停，再取消 flush 任务。
此时内存队列仍有一个事件；恢复正常 commit 并再次 flush，数据库计数为 2。

这是人工放大“提交成功到确认队列”的窗口，证明需要处理取消边界；不是声明
正常运行已经普遍重复计数。单纯使用 shield 包住 SQL await 仍不足够，因为
外层调用可以收到 CancelledError，队列确认代码不一定执行。

统计改造必须将以下操作作为同一个有明确生命周期的批次任务：

- 固定本批事件快照，事务外完成聚合、行编码和权限参数整理。
- 后台线程独占连接，连续执行本批 SQL，成功提交或完整回滚，最后关闭连接。
- 成功后仅移除该快照中已提交的事件对象，保留期间新追加的事件。
- 保留正在执行批次的任务引用；并发 flush 加入同一个任务，不重复提交快照。
- 外层取消不取消批次确认任务；关闭过程等待批次结果与队列确认完成，再结束。
  不能在后台线程结果未知时将同一批次作为失败重新发出。
- 确认失败且已回滚才能重试累加型统计。无需为第一阶段优化引入数据库迁移；
  若未来要求跨进程崩溃恢复的恰好一次计数，再设计持久化批次 ID 和去重记录。

权限表缓存当前在事务提交前置为已建立，且使用 threading.Lock 跨 await。
改造时应在同步初始化边界处理建表，并在成功提交后更新缓存，避免回滚后缓存
仍声称表存在；不能只是机械地把 await 删除。

### 日程取消与交接

领取任务提交后，如果调用方被取消而没拿到 claims，后台线程不会因此自动撤销
已提交的租约。需要由领取操作持有结果直到完成交接：正常路径交给执行任务；
取消路径对尚未启动的 claims 按 lease_token / run_id 条件释放并记录中断。
已有 `release_claim` 的条件更新可作为基础，不能无条件清除租约，也不能把
已经交给执行器的任务再次释放。释放失败必须可观察，并保留现有租约过期恢复。

### 事件补写的独立约束

事件以 (run_id, seq) 幂等写入，与累加型统计不同，可以安全重放相同批次。
建议仅对确认为 SQLite BUSY 的错误进行有界退避，不能将全部 OperationalError
都当成临时锁错误。每次重试先确保旧事务结束，在事务之外等待；保持只有一个
实际写入批次在途，并让新的事件追加到后续队列。

单次数据库 busy_timeout 暂不提高。重试的总期限必须覆盖 SQL 等待和退避，
由正常后台补写与结束阶段各自定义；不能在多层各加几次重试而意外拉长结束时间。
具体期限应在缩短事务后用 QEMU 数据确定，不能宣称现在已验证某个固定秒数。
最终持久化仍失败时保留可观察错误，不得标记持久化成功或无声丢弃批次。

## 实施边界与验收

第一阶段：统计批次连续提交和取消确认；日程只读预检查、连续领取和取消交接。
先保留共享数据库、WAL、同步级别和现有等待上限，不直接替换为全局单写队列。
Inbox 已有写入线程，但它按会话创建，并非覆盖所有进程的统一数据库写入器；
将它扩展为全局设施会增加关闭、排队、公平性和跨进程协调的改造范围。

第二阶段：有针对性的事件退避补写。会话合并事务暂不一起重构，依赖最新状态的
读改写不能移到事务外；后续仍超预算时再单独优化并发合并。

验收分两部分：

- 确定性测试：空日程在其他连接持锁时仍可返回；并发仅一方领取；任意写入阶段
  故障完整回滚；统计提交后取消不重复计数；提交期间追加事件不丢失；领取取消
  不留下无主租约；事件失败后补写序号连续，永久错误不无限重试。
- QEMU 对照：相同配置与工作负载，多轮记录事务持锁分布、BUSY 次数、事件
  最终落库数量和结束阶段耗时；另做有实际工具调用的负载。初步目标是常见
  写事务 p95 低于现有 1 秒事件等待预算，但这是验收目标，并非已经实现的结果。

参考：[SQLite 事务](https://www.sqlite.org/lang_transaction.html)、
[WAL 并发说明](https://www.sqlite.org/wal.html)、
[Python asyncio 取消屏蔽](https://docs.python.org/3/library/asyncio-task.html#shielding-from-cancellation)。

## 已实施：事务执行与提交归属

共享后端现已修改统计批次及日程领取路径：

- 统计聚合、参数转换、SQL 和提交由同一后台调用执行，连接在该线程内建立并关闭。
  SQL 之间无需事件循环推进。权限表使用幂等建表，批次不依赖提交前置位的缓存。
- 统计 flush 为一个共享的在途任务，包含提交和原批次队列确认；并发 flush 加入
  同一任务。调用方连续取消也先等该任务得到明确结果，再传播取消。
- 日程为空时仅执行只读查询；有候选才开启写事务并重新验证全部条件。
  租约和运行日志连续原子写入；取消发生在领取结果交接前时，按原租约条件释放。
- 未提高 busy_timeout，未新增事件重试，未改变统计口径、日程间隔、领取条件、
  运行标识生成规则、会话合并或事件日志内容。

新增 7 个确定性测试覆盖：空扫描不争写锁、统计提交后重复取消及并发 flush、
新增事件保留、统计完整回滚、领取取消后的释放与重领、领取日志失败回滚、
事件循环停止推进时后台仍可提交、预检查后任务被暂停时重新核验。
连同既有统计、日程、可观察性及事件恢复测试，共 44 项通过。

QEMU 使用隔离源码目录和临时数据库验证修改后的实现：
空日程在其他连接仍持写锁时 0.032 秒返回；一个统计事件提交后取消，再刷新，
数据库净增计数为 1，待提交队列为 0。没有替换正在运行的 APK 或真实工作区数据库。
这些验证确认已覆盖路径的改进，不代表所有业务写事务都已消除锁竞争，也不是
完整 APK 上多轮真实聊天的性能验收。后续需要打包后执行该部分验收。
