# Android QEMU 性能分层调查（2026-09-10）

环境：Android 15 ARM64 专用模拟器，内层 Linux QEMU 4 vCPU / 4 GiB，
已修复 CMLE 非法指令的 Cyrene Preview。以下时间不代表真机性能。

## 后台任务同步

对 Python 主线程做每秒一次的临时调用栈采样，发现
`BackgroundPluginHost._desired_bindings` 在同步和关闭插件时重复执行
`Path(registered.source).resolve()`，多个工具会重复解析同一插件文件。
即使加载失败列表为空，原实现也会解析所有来源路径。

已修改为：没有失败来源时无需解析；存在失败来源时，每次同步内按来源去重。
缓存不跨同步保留，因此符号链接变更和后续加载失败仍会重新判断。
插件启停、任务间隔、任务内容和失败过滤规则不变。

QEMU 内对同一函数的控制实验：500 个普通工具，3 次扫描取平均。

| 实现 | 每次扫描 |
|---|---:|
| 原实现 | 0.574590 秒 |
| 修复后 | 0.000975 秒 |

这仅是该代码段的对照，不是完整应用、模型或浏览器的提速倍数。
相关聚焦测试共 32 项通过，包括插件生命周期、后台任务和来源过滤。

## 仍需区分的耗时

- 启动采样中还出现模块导入与插件 JSON Schema 校验开销。这是启动阶段的
  观察，未通过跳过校验或禁用插件来换取速度。
- 旧会话日志中的 SQLite 锁等待发生在持久化事件批量写入处。后续已复现同库异步事务
  与事件写入冲突，详见 [数据库锁调查](android-sqlite-lock-findings.zh-CN.md)。
  不能将其全部归因于后台路径解析。
- Chromium 启动在不同轮次约为 16、26、75 秒，不能用单次结果概括。
  旧测试在 30 秒导航等待下超时；90 秒诊断等待收到 HTTP 200 后，读取正文
  仍可能超时，HTTP 状态不等于可交互页面已经就绪。
- MiniMax-M3 曾先尝试系统浏览器命令，再发现内置工具。这属于模型选择的
  额外步骤，与原生崩溃、网络或数据库等待不能合并计算。
- 同一 guest 的独立 curl 请求：B 站首页 DNS 0.579 秒，TCP 连接累计
  0.978 秒，TLS 完成累计 5.797 秒，首字节 5.890 秒，总计 5.916 秒，
  HTTP 200。阶段值为从请求开始的累计值，不能相加。单次结果说明连接可用，
  不能排除浏览器多资源加载时的网络成本，也不能把所有延迟归因于 DNS。

## 诊断边界

最终分层测量复用同一个 Chromium 标签页，依次访问测试 HTTP 服务、
example.com 和 B 站。先等待 commit，再等待 DOMContentLoaded，最后读取
标题与正文（各有独立 5 秒诊断预算）。Chromium 启动 59.196 秒。

| 页面 | 收到导航响应 | DOMContentLoaded | 完成读取 |
|---|---:|---:|---|
| guest 本地静态 HTML | 0.544 秒 | 1.009 秒 | 1.341 秒，标题、正文正确 |
| example.com | 1.105 秒 | 1.429 秒 | 1.738 秒，标题、正文正确 |
| bilibili.com | 2.286 秒 | 13.910 秒 | 标题读取超过 5 秒；总观察 19.264 秒 |

三个页面都返回 HTTP 200。不能将 B 站后续读取超时描述为“没有收到网页”
或 DNS 失败。重页面资源与脚本执行、模拟执行开销仍是后续重点；本次未做
渲染进程内部 CPU profile，不能精确归因到某个网站脚本。
建议优先验证工作区已有的 Android 原生浏览器桥接，让网页渲染离开 guest
TCG 路径，同时保留 Workbench 和 Agent 的工具接口。不能以本次数据宣称
该新路径已通过或保证其性能。

临时主线程采样仅存在于测试虚拟机，未加入产品。大采样文件经串口传输会
干扰诊断，因此后续改为在 guest 内聚合，只读取小结果。
当前测试 APK 仍走 Linux 内的 Playwright/Chromium；工作区已有 Android
原生浏览器桥接改动，不在本轮旧 APK 对照中，不能当作已完成实机验证。

本轮后台同步源码修复尚未重新制作完整运行时镜像或发布 APK。
