# Android 启动耗时与进度设计

## 结论

移动端当前在本机 QEMU TCG 中启动完整 Debian 与 Python Workbench。ARM64 运行时仍使用软件模拟，当前配置为一个虚拟 CPU。启动不能只按 WebView 加载速度来分析。

应分别测量三种情况：首次安装后的准备、进程被系统回收后的冷启动、后台运行环境仍在时重新打开。它们的耗时来源不同，不能共用一个预计倒计时。本轮已获得一组 PLZ110 真机首次启动数据，但没有同条件旧版对照，因此不承诺具体提速百分比。

## 当前启动链路

1. 连接 Android 后台服务，验证签名清单。
2. 首次安装时复制压缩资源、校验摘要，解压出 8 GiB 的稀疏模板盘。已有模板时重新校验磁盘摘要。
3. 首次启动该镜像时，将模板复制成持久化工作盘；已有工作盘则直接复用，不覆盖用户数据。
4. 启动 QEMU，等待 Linux 和串口控制服务就绪。
5. 启动 Python 后端，等待认证健康检查成功。
6. 建立本地代理、打开 WebView，加载 Workbench。

运行环境仍在时可复用内存中的镜像、工作盘、VM 和后台服务，跳过资源安装与系统引导。进程重建则会再次验证只读资源。不能通过删除工作盘、降低签名验证或不检查损坏资源来换取启动速度。

## 本次实现

- 将圆形等待图标改为水平进度条，并显示当前准备阶段，中英文均覆盖。
- 复制资源、校验文件、解压镜像、创建工作盘使用实际字节数计算**当前阶段**进度；不是总耗时百分比。
- 连接服务、Linux 引导、Python 初始化没有可信工作量，显示不定进度条，不使用定时递增的虚假百分比。
- WebView 加载阶段使用 WebView 回报的页面进度。只有页面加载成功才退出准备页；错误仍提供重试。
- 进度通过 Binder 单向回调传递，与最终请求结果分开；长任务不会因为进度轮询超时而被取消。回调按时间节流，减少跨进程通信。
- 复制安装资源时同时计算摘要，解压时同时计算解压后摘要；仍核对签名清单中的摘要及解压大小，仍采用临时文件与重命名发布结果。
- 首次安装因此减少一次压缩资源文件读取，以及一次完整 8 GiB 模板盘读取。这里是逻辑读取量，不能直接换算为秒数或物理磁盘写入量。
- 校验已有文件的读取缓冲从 8 KiB 增至 64 KiB；保留每次进程重建后的完整资源校验。
- 在长时间资源准备之前启动前台服务，避免准备阶段仅靠绑定服务维持生命周期。失败仍停止服务，运行中的工作仍由原有生命周期机制管理。
- `CyreneStartup` 日志记录阶段首次出现时间与请求结束时间，不记录凭据、对话或工作区内容。

## 下一步优先级

### 先实测，定位占比

记录首次安装、进程冷启动、保留后台的重新打开各至少三次，报告中位数与范围，分别记录资源处理、Linux 引导、Python 就绪、页面呈现。使用同一台手机、相同构建、相同镜像与存储余量，并记录机型、系统、内存和温度。仅在独立测试应用或测试设备上创建新的工作区进行首次启动测试，不清除使用中的数据。

日志示例：`adb logcat -s CyreneStartup:I CyreneQemuSerial:I`。HEALTH_CHECK 与 DESKTOP_START 各有独立的请求计时，需结合日志时间戳观察两阶段边界；页面加载完成还需单独测量。此次日志提供定位依据，不是完整性能基准报告。

### 第一优先：缩短 Python 启动临界路径

在现有 ARM64 镜像内分析 Python 导入与后端就绪前的工作。检查 OCR、语音、浏览器及其他大型依赖是否在尚未使用时就加载；只延后确实不影响主页面和基础会话的初始化，首次使用对应功能时仍必须可用。先验证导入占比再调整，不能为了快速进入空壳而隐藏功能失败。

同时检查安装镜像中 Python 字节码是否齐全，若运行时仍大量编译，可在镜像生成时预编译。现有依赖安装可能已经生成部分字节码，不能先假定全部缺失。

### 第二优先：缩短 Linux 引导

记录 guest 的 systemd 启动链及耗时，检查非必要服务和等待项。先确认网络、DNS、随机数、串口控制和文件系统依赖，逐项移除真正不需要的引导工作。保留完整工具使用能力。

### 第三优先：减少模板与工作盘的首次复制

研究只读基础镜像加写时复制工作盘，或仅在需要恢复时才生成模板。可以减少首次启动的逻辑 I/O 与空间占用，但需要验证当前 JNI/QEMU 对镜像格式的支持、断电恢复、版本更新与数据迁移，不能直接替换现有磁盘格式。

### 后续评估

- 多虚拟 CPU / 多线程 TCG：需要验证当前引擎能力，且对串行 Python 导入未必有效，不能仅增加 CPU 数就承诺提速。
- VM 快照：需要处理认证令牌、网络、文件系统一致性、应用升级、版本绑定和后台任务恢复，不适合作为第一步。
- 更换运行时架构：若软件模拟占据绝大多数耗时，可另行验证 Android 原生 Python 或其他承载方式；这是兼容性工程，需要完整回归桌面依赖与工具，不能以裁剪功能替代。

## 验证边界

本轮本地测试覆盖稀疏盘零区、短读取、截断、流式摘要、单调字节进度、大于 4 GB 的计数、未知阶段进度与 Binder JSON 往返；Android 模块测试同时编译 AIDL、Kotlin 和资源。进度条及进入 Workbench 已完成一次真机视觉验证；同条件新旧版本对照和多次冷／热启动测量仍待完成。


## 2026-09-10 真机观察

设备为 PLZ110，Android 16、ARM64。测试安装为独立 `ai.cyrene.mobile.preview`，使用 beta18 发布 APK 中原样提取的签名运行资源，保留原版与原版工作盘；没有清除原版数据。Preview 的包名和安装显示名通过本地临时 Gradle init 脚本设置，不改变正式发布包标识。

| 阶段 | 本次耗时 |
| --- | ---: |
| 签名资源准备、复制与解压（HEALTH_CHECK） | 39.749 秒 |
| 创建工作盘及 VM 引导，直到进入 backend 阶段 | 43.895 秒 |
| backend 阶段到认证健康检查成功 | 219.210 秒 |
| 两个启动请求合计，到后端就绪 | 302.857 秒 |

这是一次首次启动观察，不是多次采样的性能结论。页面最终进入 Workbench 已由屏幕截图确认，但页面首帧时间没有单独记录。此前旧版 QEMU 仍在后台，手机交换内存使用量较高，因此不能把这个样本直接当成隔离条件下的耗时，也不能宣称已经获得与旧版相比的加速比例。旧版后台随后已停止，原版数据未删除。

进度条截图确认“创建工作空间 82%”与实际字节进度同步；后端阶段使用不定进度条，最后成功退出准备页。启动日志表明后端阶段占约 72.4%，下一轮应优先细分这段时间。

后端阶段包括启动控制命令、systemd 服务启动、Python 初始化和健康探测，不等同于纯 Python 导入时间。通过现有 debug Binder 探针继续查询 guest 日志时，探针在关闭绑定时报告 `Service not registered`，本轮未能取得可靠的内部耗时细分。必须先修复诊断通道或增加 guest 启动时间戳，再决定具体延迟加载哪些模块，不能根据 CPU 占用直接下结论。


## 重新进入的复用优化

- Workbench 会话、代理和启动任务改为应用进程级所有者，Activity 重建不再取消后台启动或换一个代理端口。
- 返回键将任务移到后台，保留当前 WebView；Home 返回已有任务、重复点击应用图标和旋转屏幕继续使用现有页面。
- 活跃后端在 DESKTOP_START 开头通过认证健康检查直接返回原有端点，不再执行镜像校验、串口 ping 和 systemd 启动命令。冷启动仍验证签名资源。
- 恢复页面时在后台检查后端状态；状态正常不修改页面或代理。失效时合并为一次恢复请求。只读状态查询不再触发镜像准备，其超时取消也不终止 VM。
- Binder 客户端统一绑定应用 Context，避免诊断 Activity 关闭后解绑失效。
- 单元测试增加重复进入共享启动、健康连接保持、失效重连去重及显式停止后不复活的覆盖。

边界：强制停止应用、系统终止整个运行环境、安装更新仍需冷启动。若仅前端进程被回收，网页仍须重新创建，但活跃后端可以复用；不承诺在系统回收后保留内存中的网页。


### 重新进入验证结果与待办

- 新版 Preview 已覆盖安装，启动中按 Home 后重新进入，Android 报告 `LaunchState: HOT`，`TotalTime: 71 ms`；前后主进程 PID 19355、运行时 PID 31369 均未变化，没有新增启动阶段日志。此数据只代表任务恢复，不是冷启动耗时。
- 更新安装后的这次冷启动：资源校验约 10.9 秒，随后系统引导到 backend 阶段约 51.3 秒；backend 持续未就绪，因此尚未完成“已进入 Workbench 后 Home / 返回键重新进入”的最终真机验证。
- 已进一步将桌面启动串行锁与 VM 管理锁分离，允许等待健康检查时诊断 guest 状态；增加后端启动命令完成日志和定期 systemd 状态检查，若服务已失败或停止则报错，不继续等待整个健康检查超时。服务检查仅记录状态和退出码，不输出令牌或用户内容。
- 上述诊断增补构建和 13 项相关测试通过，但 USB 调试连接中断，增补包尚未覆盖到手机。


### 连接恢复后的最终真机验证（16:26–16:33）

诊断增补 APK 已在保留 Preview 数据的情况下覆盖安装。应用启动请求到认证后端就绪为 299.742 秒，首次 WebView 页面加载完成又用了约 38.7 秒。这个冷启动样本仍很慢，不能称为冷启动问题已修复。

- 资源校验到 VM boot：9.669 秒；进入 backend：42.628 秒；启动控制命令在约 48.4 秒完成。
- guest 日志显示 Web UI starting 到 Web UI at 之间约 157.2 秒；这是应用创建、插件加载和路由配置等工作所在的区间，尚未细分，不能全部归因于 Python 导入。
- 插件 startup host 记录约 56.3 秒；终端守护进程在恢复时曾报告连接超时，最终应用 startup 完成、HTTP 监听建立、认证健康检查成功，原终端页面恢复。
- debug Binder 诊断调用成功，之前的解绑异常没有再出现。探针 Activity 会短暂覆盖为一个空白页再返回，这次已向用户说明；它不是正式启动流程的一部分。
- 页面就绪后按 Home、等两秒再进入：Android HOT，任务恢复 70 ms；按返回键、等两秒再进入：HOT，49 ms。两次前后主进程 PID 20708、运行时 PID 23250 不变；workbench_page_loaded 总共仍只有一次，没有新的 boot 或 desktop_start。状态检查分别约 416 ms、300 ms，在恢复后后台完成。
- 这里的 70/49 ms 是 Android 的任务恢复计时，不是网页首次渲染速度，也不是多次统计结果。仅验证短暂离开后返回；长时间后台、系统回收和重启仍需单独测试。

本次验证使用 16:17 构建的诊断 APK、原 beta18 签名资源、单个模拟 CPU 和 2 GiB guest RAM。工作区随后出现的 4 CPU / 4 GiB 设置不在这个 APK 内，不能将上述结果当作它的验证结果。
